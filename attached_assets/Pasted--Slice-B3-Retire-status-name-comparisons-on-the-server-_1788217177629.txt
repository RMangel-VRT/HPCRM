# Slice B3 — Retire status-name comparisons on the server

**This slice is server-only and shares no files with Slice V3 (list visuals).**
`artifacts/api-server/**` only. It touches **zero** client files, so it can run alongside
or in either merge order with V3 without conflict. If you find yourself editing anything
under `artifacts/highplains-crm/`, stop — you are in the wrong slice.

## Why

Slices A/A2/B1/B2 moved ticket-*type* identity off display names onto `type_key`, and
backfilled `status_key` onto `ticket_type_statuses`. The status side of the server was
never finished: the code still identifies workflow statuses by comparing
`status.name === "Ready for Billing"` and friends. Those strings are user-editable —
renaming a status in the admin UI silently breaks invoice auto-creation, scheduling
detection and the RFP decision branches.

There is already an `isSeededTicketType()` helper for the type side. This slice adds the
status-side equivalent and routes every comparison through it.

**Behaviour must not change.** The helper is key-first with a display-name fallback, so an
unkeyed legacy row resolves exactly as it does today.

## Step 2 — Add the status-side helpers

In `artifacts/api-server/src/shared/ticketCapabilities.ts`, after `STATUS_KEY_BACKFILL`,
add:

```ts
export interface TicketStatusIdentity {
  name: string;
  statusKey?: string | null;
}

/**
 * Every display name that has ever mapped to a given status key, derived from
 * STATUS_KEY_BACKFILL so there is exactly one source of truth. Used only for the
 * legacy fallback path — a row with a non-null status_key never consults this.
 */
const STATUS_NAMES_BY_KEY: Record<string, Set<string>> = (() => {
  const out: Record<string, Set<string>> = {};
  for (const byName of Object.values(STATUS_KEY_BACKFILL)) {
    for (const [name, key] of Object.entries(byName)) {
      (out[key] ??= new Set<string>()).add(name);
    }
  }
  return out;
})();

/** Key-first. A non-null key is authoritative; only unkeyed rows fall back to name. */
export function isSeededStatus(
  status: TicketStatusIdentity | null | undefined,
  key: string,
): boolean {
  if (!status) return false;
  if (status.statusKey != null) return status.statusKey === key;
  return STATUS_NAMES_BY_KEY[key]?.has(status.name) ?? false;
}

/** Array convenience mirroring findSeededTicketType. */
export function findSeededStatus<T extends TicketStatusIdentity>(
  statuses: readonly T[],
  key: string,
): T | undefined {
  return statuses.find(s => isSeededStatus(s, key));
}
```

Deriving `STATUS_NAMES_BY_KEY` from `STATUS_KEY_BACKFILL` rather than hardcoding a second
list is the point — a new seeded status added to the backfill map is automatically
understood by the fallback, with no second place to update.

`??=` on an index signature is supported by this repo's TS target; if the baseline
typecheck disagrees, use an explicit `if (!out[key]) out[key] = new Set<string>();`.

Notes that matter:

* **`isSeededStatus` handles `null`/`undefined` internally**, so `newStatus?.name === "X"`
  becomes `isSeededStatus(newStatus, "x")` with **no** optional chaining. Writing
  `isSeededStatus(newStatus?, …)` is a syntax error; writing
  `newStatus && isSeededStatus(...)` is redundant but harmless.
* **L6986 and L7044 are the invoice auto-creation path** that Slice B1 worked on. L6986
  gates whether an Invoice ticket gets created when a ticket reaches Invoicing; L7044
  feeds the Ready-for-Billing branch. Convert them exactly as tabled and change nothing
  else in those expressions — in particular leave `isProjectTypeForInvoice`,
  `isEstimateRequestTypeForInvoice` and `isInvoiceTicketType` untouched. They are already
  key-based from B1/B2.
* **L269–270** are inside an invoice-status ensure/seed helper. Converting them is
  correct — a re-run against a renamed status should still find it by key.
* `let` vs `const`: L269–270 use `let` because they are reassigned if not found. Keep
  `let`.

Add to the file's existing import from `../shared/ticketCapabilities` (or `./shared/...`
per that file's convention — **copy the path already used in `routes.ts`**, do not invent
