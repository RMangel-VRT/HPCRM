# Replit Prompt — Extra Billable Campaign, Slice 1: Foundation

## Context

We are adding a new campaign category — **Extra Billable** — to the existing Campaign system. The use case: any time a batch of properties needs one-off billable work that falls outside contracts (heavy spring snow branch removal, hail damage cleanup, seasonal cleanups, ad-hoc bid batches, etc.), an admin creates one campaign, picks the customers, builds custom field crews for the job, divides properties among the crews, and the system later turns each completed property into an Extra Billable ticket with its photos attached.

This is the same shape as the existing General / Chemical / Irrigation campaigns, plus the property-impact-to-ticket pattern that already works for Snow Events. We are not building a parallel system — we are extending the campaign tables and adding a new category that wires to the existing Extra Billable ticket type.

This is **Slice 1 of 5**. Slice 1 lays the schema foundation and the basic admin flows: creating an Extra Billable campaign, picking customers, building per-campaign custom crews, defining the per-campaign checklist, and seeing a basic table view of properties with their crew assignments. **No drag-drop crew assignment UI in this slice** (Slice 2). **No property grid with drop zones in this slice** (Slice 3). **No ticket generation in this slice** (Slice 4). The deployable end-state of Slice 1 is: an admin can fully set up the campaign and its crews. The crew leader can already see and act on their assigned items via the existing `CampaignItemDetail.tsx` mobile flow because the underlying tables are the same.

This slice should land in a deployable, production-quality state. Do not stub anything you say you've built. If a piece can't be cleanly extended, document it in Deliverables and propose an alternative — do not create parallel tables.

### 2. New columns on `campaign_items`

Add the following four columns. **Inspect first** to make sure nothing similar already exists with a different name — if it does, reuse it and call out the deviation in Deliverables.

- `assignedCampaignCrewId` — `varchar`, FK → `campaign_crews.id`, nullable, `ON DELETE SET NULL`. The crew this property is assigned to. Null = unassigned.
- `billingStatus` — `text`, not null, default `"not_created"`. `$type<"not_created" | "ticket_created" | "invoiced" | "paid">()`. Mirrors `snow_event_property_impacts.billingStatus`.
- `ticketId` — `varchar`, nullable. References `tickets.id` via `ON DELETE SET NULL` (use a deferred FK if the table-load order requires — match the existing pattern in `snow_event_property_impacts`). The Extra Billable ticket generated from this item, when one exists.
- `estimatedAmount` — `numeric(10, 2)`, nullable. Per-property dollar estimate the admin can enter at setup time. Optional; left null in v1, filled in by the admin opportunistically. Slice 4 will use this if present when creating tickets.

Add an index `campaign_items_assigned_campaign_crew_id_idx` on `assignedCampaignCrewId`. Update `insertCampaignItemSchema` accordingly with `.nullable().optional()` for all four.

### 3. New table: `campaign_crews`

Per-campaign custom crew. The admin builds these fresh on every Extra Billable campaign — they are **not** the same thing as `maintenance_crews`.

```ts
export const campaignCrews = pgTable("campaign_crews", {
  id: varchar("id").primaryKey().default(sql`gen_random_uuid()`),
  campaignId: varchar("campaign_id").notNull().references(() => campaigns.id, { onDelete: "cascade" }),
  companyId: varchar("company_id").notNull().references(() => companies.id, { onDelete: "cascade" }),
  name: text("name").notNull(),
  color: text("color").notNull().default("#2563eb"),
  leaderUserId: varchar("leader_user_id").references(() => users.id, { onDelete: "set null" }),
  displayOrder: integer("display_order").notNull().default(0),
  createdAt: timestamp("created_at").notNull().defaultNow(),
}, (table) => ({
  campaignCrewsCampaignIdIdx: index("campaign_crews_campaign_id_idx").on(table.campaignId),
  campaignCrewsCompanyIdIdx: index("campaign_crews_company_id_idx").on(table.companyId),
  campaignCrewsNameUnique: unique().on(table.campaignId, table.name),
}));
```

`color` defaults to a blue but the admin can override per crew (used for visual distinction in Slice 2's assignment board). `leaderUserId` is nullable so a crew can be created and named before the leader is picked, but for any crew that has properties assigned to it, leader **must** be set — enforce in the API handlers, not in DB constraints (so partially-created crews don't break the schema).

### 4. New table: `campaign_crew_members`

Pure join table. The leader is also one row in here (so demoting a leader doesn't accidentally strip them from the crew). The leader's leadership is recorded by `campaign_crews.leaderUserId`, not by a flag here.

```ts
export const campaignCrewMembers = pgTable("campaign_crew_members", {
  id: varchar("id").primaryKey().default(sql`gen_random_uuid()`),
  campaignCrewId: varchar("campaign_crew_id").notNull().references(() => campaignCrews.id, { onDelete: "cascade" }),
  userId: varchar("user_id").notNull().references(() => users.id, { onDelete: "cascade" }),
  createdAt: timestamp("created_at").notNull().defaultNow(),
}, (table) => ({
  uniqueCrewMember: unique().on(table.campaignCrewId, table.userId),
  campaignCrewMembersCrewIdIdx: index("campaign_crew_members_crew_id_idx").on(table.campaignCrewId),
}));
```

When a crew is created, **automatically insert a member row for the leader** if `leaderUserId` is set on creation. When the leader is changed via PATCH, automatically add a row for the new leader if not already present. Never silently delete a member row when a leader is replaced — keep the demoted user as a regular member; admin must explicitly remove them.

## API endpoints

All endpoints check `req.isAuthenticated()` and read `companyId` from `req.user as UserWithContext`. Match the existing route-file structure — these can live alongside the existing campaign routes in `server/routes.ts` (do not create a new file unless the existing pattern demands it).

### 1. Extend campaign creation

The existing `POST /api/campaigns` endpoint accepts a `category`. Add `"extra_billable"` to the accepted Zod enum. When category is `"extra_billable"`:

- `assignedToId2` is allowed (already supported).
- A `customerIds: string[]` array is required (already supported by the existing flow — verify this; if not, accept it on this category only). Each customer becomes a `campaign_items` row with `status: "pending"`, `billingStatus: "not_created"`, `assignedCampaignCrewId: null`.
- A `checklistTasks: { label: string; order: number }[]` array is optional — when provided, create `campaign_checklist_tasks` rows. Reuse the same flow the irrigation campaign uses (see `CampaignsList.tsx` ~line 411–413).

No change needed for general/chemical/irrigation campaigns.

### 2. Crew CRUD

```
GET    /api/campaigns/:campaignId/crews
POST   /api/campaigns/:campaignId/crews
PATCH  /api/campaigns/:campaignId/crews/:crewId
DELETE /api/campaigns/:campaignId/crews/:crewId
```

- `GET` returns `CampaignCrewWithMembers[]`. Compute `leaderName` from the joined user, `members` from `campaign_crew_members` joined with users, `itemCount` / `completedCount` / `photoCount` from `campaign_items` aggregations (LEFT JOINs with COUNT). Order by `displayOrder` then `createdAt`.
- `POST` body: `{ name, color?, leaderUserId?, memberUserIds?: string[] }`. Validates name is non-empty and unique within the campaign. If `leaderUserId` is set, automatically inserts a `campaign_crew_members` row for the leader (don't require client to also pass them in `memberUserIds`). `displayOrder` defaults to (max existing order + 1).
- `PATCH` body: `{ name?, color?, leaderUserId?, memberUserIds?: string[], displayOrder? }`. When `leaderUserId` changes: ensure new leader is also in members (insert if not). When `memberUserIds` is provided: full replace, but **never remove the current leader** — return a 400 if the new member set excludes the leader. The client must change leader first, then trim members.
- `DELETE` is rejected with 400 if any `campaign_items` row still references the crew via `assignedCampaignCrewId`. The client should reassign or unassign first. (Slice 2 builds the bulk-reassign endpoint; Slice 1 client uses per-row reassignment via the basic table view.)

Authorization: admin/office only.

### 3. Crew member CRUD (convenience)

```
POST   /api/campaigns/:campaignId/crews/:crewId/members
DELETE /api/campaigns/:campaignId/crews/:crewId/members/:userId
```

Used when the admin opens an existing crew and wants to add or remove one user without doing a full PATCH. Validation: cannot remove the current leader via this endpoint (must change leader first). Authorization: admin/office.

### 4. Single-item crew assignment (basic)

```
PATCH /api/campaigns/:campaignId/items/:itemId/assigned-crew
```

Body: `{ assignedCampaignCrewId: string | null }`. Updates one row. Authorization: admin/office. Slice 2 will add the bulk-assign endpoint; this one stays for one-off reassignments and is what the basic table view in Slice 1 uses.

### 5. Field-leader scoping for item access

This is the central authorization rule for the new category. It **augments** the existing campaign item access checks.

- **Read access** to a `campaign_items` row in an `extra_billable` campaign: admin/office (any), OR the user is in `campaign_crew_members` for the row's `assignedCampaignCrewId`.
- **Write access** (photo upload, mark complete, toggle checklist, edit notes, set exceptionType): admin/office (any), OR the user is `campaign_crews.leaderUserId` for the row's `assignedCampaignCrewId`. **Crew members who are not the leader cannot write.**

Implement this as a helper `canAccessExtraBillableCampaignItem(user, item, mode: "read" | "write")` and call it inside every campaign-item handler that touches a row whose parent campaign has `category: "extra_billable"`. For other categories, the existing access rules still apply unchanged.

Apply the same filter at list-fetch time: when a `field`-role user calls `GET /api/campaigns/:id/items` (or whatever the existing list endpoint is) on an extra_billable campaign, return only items whose crew membership includes them. When a `field`-role user calls the campaigns list, an extra_billable campaign should appear if and only if they are a member of any of its crews.

Test that the leader-only write rule cannot be bypassed by a crew-member POSTing to `/api/campaigns/:cid/items/:iid/completion-photos/upload` directly.

## Patterns and conventions

- Every user-facing string goes through i18next (en + es). Where existing campaign translations already cover something, reuse the key — do not duplicate.
- Every new query filters by `companyId`. No exceptions.
- Schema additions go in `shared/schema.ts` alongside existing tables. Drizzle `pgTable` patterns must match the existing style (snake_case column names in `text(...)` calls, camelCase property names, indexes named `<table>_<column>_idx`).

- Loading states: shadcn `Skeleton`. Error states: shadcn `Alert`. Toasts: existing `useToast` hook.
- All new icons from `lucide-react`.
- Reuse the existing `apiRequest` / `queryClient` helpers from `client/src/lib/queryClient`.
- Zod schemas are shared via `shared/` where the existing code already does this.
- Use `data-testid` attributes on every interactive element following the existing convention (e.g., `data-testid="button-add-crew"`, `data-testid="row-crew-${id}"`).
- The leader-only write rule MUST be enforced server-side, not relied upon in the UI alone. Add a focused unit test (using `vitest` and `supertest`, matching the existing `mailboxAccounts.oauthReconnect.test.ts` pattern) that confirms a non-leader crew member gets 403 when attempting `POST /api/campaigns/:cid/items/:iid/completion-photos/upload` on an extra_billable campaign item.
