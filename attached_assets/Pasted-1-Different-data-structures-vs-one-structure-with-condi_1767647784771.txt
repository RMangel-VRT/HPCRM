1) Different data structures vs. one structure with conditional fields

I’d keep one core “Equipment” record for everything, and use type-specific fields that show/hide based on equipment type. That gives you the best mix of simplicity and scalability.

Why this is usually better than separate tables per type:

One list, one search, one permissions model, one ticket link model (super important).

You avoid messy edge cases later (e.g., a “truck” that becomes a “specialty vehicle,” or a mower that needs a trailer-style registration field).

Reporting stays easy (“show all equipment in repair”, “open tickets by equipment type”, etc.).

When separate data structures make sense:
Only if each type has wildly different data and you need strict requirements per type. Even then, you typically still keep a base equipment table + one optional “detail” table per type. That’s more complexity than you need right now.

✅ Recommendation:

Base Equipment fields for all types (always visible)

Type-specific sections (shown only when relevant)

Fields not relevant are simply left blank and not shown in the form UI.

3) Office users need create access (not view-only)

Got it. Update permissions to:

Admin + Shop Manager + Office: create/edit equipment records + upload files

Ops + Viewer: no access

Two implementation details I’d strongly recommend for Office:

Office can create/edit equipment records and attachments

Office should NOT be able to delete equipment (optional), only Admin/Shop Manager can retire/delete

This prevents accidental nukes while still letting office staff manage inventory.
