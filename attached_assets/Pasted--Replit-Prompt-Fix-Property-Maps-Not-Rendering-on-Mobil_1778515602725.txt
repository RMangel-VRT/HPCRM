# Replit Prompt — Fix Property Maps Not Rendering on Mobile Web

## Context

Bug: on the property-maps page (and anywhere else `LayerMapViewer` is mounted — Customer Detail, Ticket Detail, Campaign Item Detail), users on mobile browsers see the satellite/OSM basemap load fine, but the uploaded KML layers do not render. Because no layer ever produces valid bounds, the map also never auto-centers on the community — it stays parked on the default center (Kansas, zoom 4). On desktop Chrome the same customer's layers render and the map centers correctly.

We've narrowed it to three independently real problems in `client/src/components/LayerMapViewer.tsx`. Any one of them is enough to break a customer's layers on mobile; depending on the KML source, more than one applies at once.

1. **KML namespace handling.** The current parser does `kmlDoc.querySelectorAll("Placemark")` on a document parsed as `text/xml`. KML files exported from Google Earth and most other tools declare `xmlns="http://www.opengis.net/kml/2.2"` as the default namespace. WebKit (iOS Safari, all browsers on iOS, and macOS Safari) treats CSS selectors in XML documents as namespace-aware and returns zero matches. Blink (desktop Chrome, Edge) is lenient and returns matches. Result: the same code returns 0 Placemarks on iOS and N Placemarks on desktop Chrome — which exactly matches what users are reporting.
2. **KMZ files are not actually supported.** The upload UI on `PropertyMapsPage.tsx` advertises `.kml,.kmz` and the upload mutation cheerfully accepts either. But `kmlToGeoJson` in `LayerMapViewer.tsx` only handles XML text — it calls `DOMParser.parseFromString(kmlText, "text/xml")` on the response body. KMZ is a ZIP archive; parsing zipped binary as XML yields an empty document and zero features. If any community has a `.kmz` layer in their library, it has never rendered for anyone — desktop or mobile — and the symptom on mobile gets blamed on the more visible namespace bug above.
3. **Map sizing race on mobile.** `FitBounds` calls `map.invalidateSize()` and then `map.fitBounds(...)` inside a single 100ms `setTimeout`. On iOS Safari the container is often still 0-height at that moment because the page is using `100vh` heights and the URL bar collapse triggers a layout pass after first paint. `fitBounds` against a zero-size container is a silent no-op, the map keeps its default view, and even when layers eventually do render they appear off-screen. We also never re-invalidate on subsequent container resizes (rotate, URL bar collapse, layer-panel toggle).

This slice fixes all three. It also stops swallowing fetch errors so the next time something like this regresses, the developer sees it in the console and in the UI.

**Scope is strictly the viewer.** Don't touch upload, the API route, object storage, the schema, or any other map component (Mapbox-based `CustomerLocationEditor`, `VisualScopeDraft`, `CustomerRouteMap` — those use a different stack and aren't part of this bug).

### 1b. Replace `kmlToGeoJson` and `parseKmlCoordinates`

In `client/src/components/LayerMapViewer.tsx`, delete the two functions at the bottom of the file (`kmlToGeoJson` around line 500 and `parseKmlCoordinates` around line 569). Replace them with a single async function that handles both `.kml` and `.kmz` input transparently:

```ts
import { kml as kmlToGeoJsonLib } from "@tmcw/togeojson";
import JSZip from "jszip";

// Magic bytes for ZIP archives (KMZ is a ZIP containing one .kml + assets).
function looksLikeZip(bytes: Uint8Array): boolean {
  return bytes.length >= 4 && bytes[0] === 0x50 && bytes[1] === 0x4b &&
         (bytes[2] === 0x03 || bytes[2] === 0x05) &&
         (bytes[3] === 0x04 || bytes[3] === 0x06);
}

async function fetchAndParseKmlOrKmz(url: string): Promise<GeoJSON.FeatureCollection> {
  const res = await fetch(url, { credentials: "include" });
  if (!res.ok) throw new Error(`Failed to fetch KML (${res.status} ${res.statusText})`);

  const buf = new Uint8Array(await res.arrayBuffer());

  let kmlText: string;
  if (looksLikeZip(buf)) {
    const zip = await JSZip.loadAsync(buf);
    // Find the first .kml entry (typically "doc.kml")
    const kmlEntry = Object.values(zip.files).find(
      (f) => !f.dir && f.name.toLowerCase().endsWith(".kml")
    );
    if (!kmlEntry) throw new Error("KMZ archive contains no .kml file");
    kmlText = await kmlEntry.async("text");
  } else {
    kmlText = new TextDecoder("utf-8").decode(buf);
  }

  const xml = new DOMParser().parseFromString(kmlText, "application/xml");
  // Reject documents that didn't parse (browsers wrap parse errors in <parsererror>).
  if (xml.getElementsByTagName("parsererror").length > 0) {
    throw new Error("KML XML failed to parse");
  }

  const geo = kmlToGeoJsonLib(xml) as GeoJSON.FeatureCollection;
  if (!geo || !Array.isArray(geo.features) || geo.features.length === 0) {
    throw new Error("KML contained no recognizable features");
  }
  return geo;
}
```

Notes:
- `@tmcw/togeojson` is namespace-aware and handles `Placemark`, `MultiGeometry`, `Polygon`, `LineString`, `Point`, `LinearRing`, `Track`, and ExtendedData. It is what every Mapbox/Leaflet KML demo uses.
- `application/xml` is preferred over `text/xml` for DOMParser — both work, but `application/xml` has better-defined behavior across engines.
- We deliberately check for `<parsererror>` so a malformed KML fails loudly instead of silently rendering nothing.

## Phase 2 — Fix the map-sizing race on mobile

### 2a. Make `FitBounds` resize-aware

In `LayerMapViewer.tsx`, replace the existing `FitBounds` component (lines 58–69) with one that:

1. Invalidates the map size whenever the container resizes (via `ResizeObserver`).
2. Defers `fitBounds` until both the bounds are valid AND the container has nonzero size.
3. Re-fits on `fitTrigger` change (preserve existing behavior).

```ts
function FitBounds({ bounds, fitTrigger }: { bounds: L.LatLngBounds | null; fitTrigger?: number }) {
  const map = useMap();

  // Keep the map's internal size in sync with the container at all times.
  useEffect(() => {
    const container = map.getContainer();
    const ro = new ResizeObserver(() => {
      map.invalidateSize({ animate: false });
    });
    ro.observe(container);
    // Also run once on mount in case ResizeObserver doesn't fire immediately on iOS.
    requestAnimationFrame(() => map.invalidateSize({ animate: false }));
    return () => ro.disconnect();
  }, [map]);

  // Fit bounds whenever bounds become valid, the trigger ticks, or the container has size.
  useEffect(() => {
    if (!bounds || !bounds.isValid()) return;
    let cancelled = false;
    const tryFit = () => {
      if (cancelled) return;
      const size = map.getSize();
      if (size.x === 0 || size.y === 0) {
        // Container not laid out yet — try again next frame.
        requestAnimationFrame(tryFit);
        return;
      }
      map.invalidateSize({ animate: false });
      map.fitBounds(bounds, { padding: [50, 50], animate: false });
    };
    requestAnimationFrame(tryFit);
    return () => { cancelled = true; };
  }, [map, bounds, fitTrigger]);

  return null;
}
```

Do not change the `<FitBounds bounds={bounds} fitTrigger={fitTrigger} />` JSX inside `<MapContainer>` — the props are the same.

### 2b. Make the outer wrapper use `dvh`, not `vh`

In `LayerMapViewer.tsx`, the outer wrapper (line 270 and line 240) uses `fixed inset-0 bg-background z-50` for fullscreen, which is fine. But verify the *parent* containers in the consumer pages (`PropertyMapsPage.tsx`, `CustomerDetail.tsx`, `TicketDetail.tsx`, `CampaignItemDetail.tsx`) actually provide a stable height in non-fullscreen mode.

For each non-fullscreen consumer, the parent wrapping `<LayerMapViewer />` must have an explicit non-zero height. Most use a `relative` parent with no height — that's why the map sometimes shows up squished or empty on mobile until you scroll. Find each `<LayerMapViewer ... />` mount that does NOT pass `fullScreen` and ensure its parent looks like:

```tsx
<div className="relative h-[60vh] min-h-[420px] sm:h-[70vh]">
  <LayerMapViewer customerId={...} />
</div>
```

If the existing parent already has a height class (`h-[600px]`, `h-screen`, etc.), leave it. The point is: don't rely on flexbox alone to size the map container on mobile.
