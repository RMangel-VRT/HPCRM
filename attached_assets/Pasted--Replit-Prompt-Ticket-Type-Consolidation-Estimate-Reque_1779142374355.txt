# Replit Prompt — Ticket Type Consolidation (Estimate Request / Project / Project No Estimate)

## Context

The CRM currently exposes three project-shaped options on the New Ticket page that confuse operators and create redundancy in the data model:

- **Project** work type — maps to the "Project" ticket type, runs the 10-step workflow (New → Estimating → Create Proposal → Proposal Sent → Decision Received → Ready to Schedule → Work Completed → Ready for Billing → Invoicing → Closed - Lost).
- **Estimate Request** work type — maps to the *same* "Project" ticket type, runs the *same* 10-step workflow. The only behavior difference anywhere in the codebase is that Estimate Request tickets are allowed to attach documents (`routes.ts` ~line 6157) and Project tickets are not.
- **Project (No Estimate)** ticket type — separate ticket type with a 7-step workflow that skips the estimating/proposal stages (New → Ready to Schedule → Scheduled → Work Completed → Ready for Billing → Invoicing → Closed - Lost).

The "Project" and "Estimate Request" work types are operationally indistinguishable. They produce the same ticket type, the same status flow, the same fields, and the same UI experience. The descriptive copy on the New Ticket screen tries to draw a line between them but nothing in the code enforces it.

**The fix** is to collapse the redundancy and rename so the user-visible labels match what the workflow actually does:

- The current "Project" ticket type → renamed to **"Estimate Request"** (its 10-step flow IS the estimate-and-propose flow).
- The current "Project (No Estimate)" ticket type → renamed to **"Project"** (it's the preapproved-project flow; the parenthetical goes away).
- The "Project" work type → eliminated. Any existing ticket with `workType = "project"` is migrated to `workType = "estimate_request"` (no workflow change for those tickets — they're already on the 10-step flow).

After this slice, the New Ticket selector shows two project-shaped options instead of three, and the work-type → ticket-type mapping becomes an honest 1:1 for the project family.

**This slice is a rename + data migration. No new workflows are added, no stages are added or removed, no behavior changes for in-flight tickets.** Anything that would alter user-visible workflow behavior is out of scope.

Work through the phases in order. After each phase, run `npm run check` and verify the New Ticket page renders before moving on.

## Phase 3 — Data migration for existing companies

Create a new migration function in `artifacts/api-server/src/routes/routes.ts`, alongside the existing `migrate*` helpers. Name it `migrateTicketTypeRename`.

The function must be idempotent — running it twice does nothing harmful — because it will be invoked from `runStartupMigrations` (or the equivalent boot path used by your deploys) and could re-run on multiple cold starts.

For each company in `companies`:

1. **Rename "Project" → "Estimate Request"** if a ticket type named `"Project"` exists for that company AND no ticket type named `"Estimate Request"` exists for that company.
   - Update the single `ticket_types` row: set `name = "Estimate Request"`, `description = "Estimate request and proposal workflow — for work that needs pricing, customer approval, and invoicing"`.
   - Do NOT touch `ticketTypeStatuses` rows — they reference the ticket type by ID, not by name. The IDs stay the same.
   - Log: `Renamed ticket type "Project" → "Estimate Request" for company ${companyId}`.

2. **Rename "Project (No Estimate)" → "Project"** if a ticket type named `"Project (No Estimate)"` exists for that company AND (after step 1) no ticket type named `"Project"` exists for that company.
   - Update the row: set `name = "Project"`, `description = "Preapproved project work — scheduling, completion, and invoicing"`.
   - Log: `Renamed ticket type "Project (No Estimate)" → "Project" for company ${companyId}`.

3. **Migrate `workType = "project"` tickets** to `workType = "estimate_request"`:
   - `UPDATE tickets SET work_type = 'estimate_request' WHERE work_type = 'project' AND company_id = $1`.
   - Log the row count per company.

**Ordering matters.** Step 1 must complete before step 2 for a given company; otherwise step 2 will see two ticket types named "Project" briefly. Do them sequentially per company, not in parallel.

**Edge cases to handle:**

- A company that has only "Project" but not "Project (No Estimate)" → step 1 happens, step 2 is a no-op. The company ends up with only "Estimate Request" until they next hit a code path that calls `ensureProjectTicketType` (the renamed one), which will create "Project" fresh. This is fine.
- A company that already has both new names (re-run case) → all three steps are no-ops.
- A company that has "Estimate Request" but not "Project" → step 1 skips because the target name already exists. Log a warning rather than failing.

Register `migrateTicketTypeRename` in whatever boot or migration sequence your project uses (`runStartupMigrations` in `routes.ts`, or the equivalent). Run it BEFORE `seedAllTicketTypes` so we never accidentally seed a fresh "Project" alongside an existing "Project (No Estimate)" mid-rename.
