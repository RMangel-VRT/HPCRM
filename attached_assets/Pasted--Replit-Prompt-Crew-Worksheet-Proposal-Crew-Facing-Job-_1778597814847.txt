# Replit Prompt — Crew Worksheet (Proposal → Crew-Facing Job Sheet)

## Context

The Proposal Maker produces a polished, customer-facing PDF (cover, scope of work, photos, Visual Scope map, attached QB Estimate). That same content — minus the dollar figures — is exactly what the field crew needs on the day of the job, plus a handful of crew-only fields: which crew is going, when, how long it should take, what equipment/materials to load, and any special instructions.

This slice adds a **Crew Worksheet** as a first-class document type alongside Proposals and Visual Scope Sheets. A worksheet starts life as a frozen snapshot of a proposal (title, scope of work, photos, map) and then becomes independently editable by anyone who can dispatch work. The crew prints it (or downloads the PDF) on the way to the job. The worksheet never contains pricing, the estimate PDF, or the Estimate Number.

Key product decisions (already approved by the user):

- **One-way snapshot, separate record.** Creating a worksheet from a proposal copies the proposal's scope/photos/visual-scope reference into a new `crew_worksheets` row. Editing the worksheet does not touch the proposal. A single proposal may spawn multiple worksheets (e.g., re-scoped after a change order).
- **Four crew-specific field groups**: crew assignment + lead, scheduled date + estimated hours, equipment/materials checklist, crew notes / special instructions.
- **Browser print view + server-side PDF download** (mirrors the Proposal pipeline; same PDFKit + `renderVisualScope` infrastructure).
- **Three entry points**: a "Generate crew worksheet" button on `ProposalDraft.tsx`, a new top-level "Crew Worksheets" tile under `/dashboard/tools`, and a card on `TicketDetail.tsx` (when the proposal is linked to a ticket).
- **No estimate fields anywhere on the worksheet** — no `estimateNumber`, no estimate PDF attachment slot, no totals.

This must land in a deployable, production-quality state. No stubs, no `// TODO` comments hiding incomplete code paths. The new tables, routes, pages, PDF generator, and ticket-side widget must all ship together.

### 4c. `_nextCrewWorksheetNumber` implementation

```ts
async _nextCrewWorksheetNumber(companyId: string): Promise<string> {
  const year = new Date().getFullYear();
  const prefix = `CW-${year}-`;
  const rows = await db
    .select({ wn: crewWorksheets.worksheetNumber })
    .from(crewWorksheets)
    .where(and(eq(crewWorksheets.companyId, companyId), like(crewWorksheets.worksheetNumber, `${prefix}%`)));
  const maxSeq = rows.reduce((m, r) => {
    const tail = (r.wn ?? "").slice(prefix.length);
    const n = Number.parseInt(tail, 10);
    return Number.isFinite(n) && n > m ? n : m;
  }, 0);
  return `${prefix}${String(maxSeq + 1).padStart(4, "0")}`;
}
```

Import `like` from `drizzle-orm` if not already present.

### 4d. `createCrewWorksheetFromProposal` — the snapshot logic

```ts
async createCrewWorksheetFromProposal({
  proposal,
  companyId,
  createdById,
  title,
  worksheetDate,
}: {
  proposal: ProposalWithDetails;
  companyId: string;
  createdById: string;
  title?: string;
  worksheetDate?: string;
}): Promise<CrewWorksheetWithDetails> {
  const today = new Date().toISOString().slice(0, 10);
  const worksheetNumber = await this._nextCrewWorksheetNumber(companyId);
  const inserted = await db.transaction(async (tx) => {
    const [wk] = await tx.insert(crewWorksheets).values({
      companyId,
      customerId: proposal.customerId,
      createdById,
      sourceProposalId: proposal.id,
      ticketId: proposal.ticketId ?? null,
      title: title ?? `${proposal.title} — Crew Worksheet`,
      worksheetNumber,
      worksheetDate: worksheetDate ?? today,
      scopeOfWork: proposal.scopeOfWork ?? "",
      visualScopeSheetId: proposal.visualScopeSheetId ?? null,
    }).returning();

    const imageFiles = (proposal.files ?? []).filter(f => f.fileType === "image");
    if (imageFiles.length > 0) {
      await tx.insert(crewWorksheetPhotos).values(
        imageFiles.map((f, idx) => ({
          crewWorksheetId: wk.id,
          companyId,
          storageObjectPath: f.storageObjectPath,
          filename: f.filename,
          mimeType: f.mimeType,
          fileSize: f.fileSize,
          caption: f.caption ?? null,
          displayOrder: idx,
          copiedFromProposalFileId: f.id,
        }))
      );
    }
    return wk;
  });

  const full = await this.getCrewWorksheetById(inserted.id, companyId);
  if (!full) throw new Error("Worksheet vanished immediately after creation");
  return full;
}
```

GCS objects are not duplicated — both records reference the same `storageObjectPath`. If the proposal photo is later deleted, the worksheet still holds the row with a (now-broken) path; this is acceptable for v1 — the UI already renders a fallback for missing thumbnails (`onError` handler at `ProposalDraft.tsx:140`). Document this in code comments.

## Why this exists

The proposal that wins a job and the work-order the crew takes to the site are two different documents with mostly the same content but mutually exclusive audiences. Today, the crew either re-derives a job sheet by hand from the customer-facing proposal PDF (slow, error-prone, exposes pricing) or works from memory + the linked ticket. A Crew Worksheet is the missing artifact: it inherits everything the proposal already captured (scope, photos, map) without the dollar figures, and adds the four operational details that only matter on the day of the job (who, when, with what, watch out for X). Making it a separate record means the crew can mark up the worksheet — equipment loaded, notes added, scope revised after a site walk — without contaminating the customer-accepted proposal. The proposal stays the contract; the worksheet becomes the playbook.
