# Replit Slice A2 — Stable `type_key` on `ticket_types`

**Ships dark. Zero behavior change. No reader changes in this slice.**

Same shape as Slice A (`0040`), which is now a proven pattern in this repo: numbered SQL migration for DDL + backfill, a DML-only boot backfill, and the `ensure*` seeding helpers updated so new companies get the value.

## Why

Slice A gave ticket types *capability* flags — what a type can **do**. It did not give them an *identity* — which type this **is**. Those are different questions, and roughly 21 remaining comparisons ask the second one:

```ts
ticketTypes.find(tt => tt.name === "Invoice")
types.filter(t => t.name === "Estimate Request" || t.name === "Project")   // routes.ts ~L5536, runtime
```

No capability flag can answer them. `requires_invoicing = 'true'` is equally true of Estimate Request, Project and Extra Billable, so it cannot distinguish one from another.

This also unblocks the two display-name checks Slice B1 deliberately left in place — both are identity questions, and both become clean flag reads once `type_key` exists:

* `ticketType?.name === "Invoice"` in `rfbInvoiceAutoCreate.ts`
* `rfbTicketType?.name === "Extra Billable"` at `routes.ts:6975`

Migrating those is **Slice B2, not this slice.** A2 only adds and backfills the column.

## 1. Schema — `lib/db/src/schema/schema.ts`

Add the key union immediately below the existing `TerminalBehavior` type:

```ts
// Stable machine identity for the seeded ticket types. `name` is the free-text
// display label and may be renamed by a user at any time; `typeKey` is what code
// should match on. Null for ticket types a user created by hand.
export type TicketTypeKey =
  | "todo"
  | "estimate_request"
  | "project"
  | "extra_billable"
  | "invoice"
  | "rfp_request";
```

Add the column to `ticketTypes`, after `terminalBehavior` and before `createdAt`:

```ts
  typeKey: text("type_key").$type<TicketTypeKey>(),
```

Nullable, no default — same treatment as `statusKey`. Readers in later slices must tolerate null.

Extend `insertTicketTypeSchema`'s `.extend({ … })` block:

```ts
  typeKey: z.enum(["todo", "estimate_request", "project", "extra_billable", "invoice", "rfp_request"]).nullable().optional(),
```

**Index — note the table currently has no index callback.** `ticketTypes` ends with a plain `});` and no `(table) => ({ … })` argument, unlike `ticketTypeStatuses`. You need to add one:

```ts
}, (table) => ({
  ticketTypesKeyIdx: index("ticket_types_key_idx")
    .on(table.companyId, table.typeKey)
    .where(sql`type_key IS NOT NULL`),
}));
```

**Deliberately NOT unique.** A unique constraint is the right end state — one `invoice` type per company — but `migrateTicketTypeRename` has a documented branch for the case where a company ends up with both `Project` and `Estimate Request`, so duplicates may exist in real data and a unique index would make the migration fail. Step 5 includes a query to find out; uniqueness can be added later once the data is confirmed clean.

## 2. Migration — `.migration-backup/migrations/0041_ticket_type_key.sql`

New numbered file. Mirror `0040_ticket_type_capabilities.sql` exactly in style.

```sql
-- Slice A2: stable machine identity for the six seeded ticket types.
-- Idempotent: IF NOT EXISTS on DDL; backfill only writes WHERE type_key IS NULL
-- (preserves any hand-edited value).

ALTER TABLE ticket_types ADD COLUMN IF NOT EXISTS type_key text;
CREATE INDEX IF NOT EXISTS ticket_types_key_idx ON ticket_types (company_id, type_key) WHERE type_key IS NOT NULL;

-- Post-rename display names → stable keys.
UPDATE ticket_types SET type_key = 'todo'            WHERE name = 'To-Do'            AND type_key IS NULL;
UPDATE ticket_types SET type_key = 'estimate_request' WHERE name = 'Estimate Request' AND type_key IS NULL;
UPDATE ticket_types SET type_key = 'project'          WHERE name = 'Project'          AND type_key IS NULL;
UPDATE ticket_types SET type_key = 'extra_billable'   WHERE name = 'Extra Billable'   AND type_key IS NULL;
UPDATE ticket_types SET type_key = 'invoice'          WHERE name = 'Invoice'          AND type_key IS NULL;
UPDATE ticket_types SET type_key = 'rfp_request'      WHERE name = 'RFP Request'      AND type_key IS NULL;
```

## 4. Extend the two existing migration functions in `routes.ts`

**Do not add new functions.** Slice A already established both; extend them in place.

`migrateTicketTypeCapabilityColumns()` (L1449) — add one line alongside the existing `ALTER TABLE` statements:

```ts
    await db.execute(sql`ALTER TABLE ticket_types ADD COLUMN IF NOT EXISTS type_key text`);
    await db.execute(sql`CREATE INDEX IF NOT EXISTS ticket_types_key_idx ON ticket_types (company_id, type_key) WHERE type_key IS NOT NULL`);
```

`backfillTicketTypeCapabilities()` (L1469) — add a `type_key` backfill after the existing capability-flag loop. **It needs its own column-existence guard**: the function's current guard checks for `requires_customer`, which will be present from 0040 even on a database that has not yet run 0041.

```ts
    // Slice A2: stable type keys. Separate guard — 0040 may have run without 0041.
    const typeKeyCol = await db.execute(sql`
      SELECT COUNT(*)::int AS count FROM information_schema.columns
      WHERE table_name = 'ticket_types' AND column_name = 'type_key'
    `);
    if (((typeKeyCol.rows[0] as { count: number })?.count ?? 0) > 0) {
      let typeKeysWritten = 0;
      for (const [typeName, typeKey] of Object.entries(TICKET_TYPE_KEYS)) {
        const r = await db.execute(sql`
          UPDATE ticket_types SET type_key = ${typeKey}
          WHERE name = ${typeName} AND type_key IS NULL
        `);
        typeKeysWritten += (r as { rowCount?: number | null }).rowCount ?? 0;
      }
      console.log(`Ticket type key backfill: ${typeKeysWritten} type keys written`);
    } else {
      console.log("Ticket type key backfill skipped: type_key column not present yet (run SQL migration 0041 via pnpm migrate)");
    }
```

Note the `AND type_key IS NULL` guard — unlike the capability flags, which are re-asserted on every boot, an identity is written once and never overwritten.

Import `TICKET_TYPE_KEYS` alongside the existing `TICKET_TYPE_CAPABILITIES, STATUS_KEY_BACKFILL` import at the top of `routes.ts`.

## Note for the reviewer

The last query in step 4 is the one worth reading carefully. If it returns rows, some company has two ticket types claiming the same identity — which would mean `migrateTicketTypeRename` left a conflict behind. That is worth knowing before Slice B2 starts doing `find(t => t.typeKey === …)` lookups that assume a single match.
