## API endpoints

### 1. New: my active batches summary

```
GET /api/me/extra-billable-batches
```

Returns campaigns where:

- `category === "extra_billable"`
- The current user is a member of any of the campaign's `campaign_crews` via `campaign_crew_members` (admin/office see all extra_billable campaigns regardless of crew membership — they get the same shape, just unfiltered)
- The campaign's `status === "active"`

Response shape:

```ts
{
  batches: Array<{
    campaignId: string;
    campaignTitle: string;
    windowStart: string;     // ISO date
    windowEnd: string;       // ISO date
    crewName: string;        // the user's crew name on this campaign
    crewColor: string;
    isLeader: boolean;       // true if the user is leaderUserId of the crew
    assignedItemCount: number;
    completedItemCount: number;
    pendingItemCount: number;
    photoCount: number;      // sum of photos across the user's assigned items in this campaign
    nextDueDate: string | null; // earliest pending item's targetDate or campaign.windowEnd
  }>;
  totalAssignedItems: number;
  totalPendingItems: number;
}
```

This endpoint is what powers the dashboard widget (§1 below) and the dedicated "My Batches" list (§3 below). Compute it in a single query per user — do not make N+1 calls.

Authorization: any authenticated user. Field-role users get filtered results; admin/office get unfiltered results (every active extra_billable campaign in the company).

### 2. (No change) Reuse existing endpoints

The campaigns list (`GET /api/campaigns`) already filters correctly per Slice 2. The campaign detail (`GET /api/campaigns/:id`) already filters items per Slice 2. The single-item endpoint (`GET /api/campaigns/:id/items/:itemId`) already enforces auth via `canAccessExtraBillableCampaignItem` per Slice 1. Slice 5 doesn't touch these.

- Header: title + a count badge of total active batches (right-aligned).

  - Color swatch from the user's crew on that campaign (5px wide left bar)

- Loading: Skeleton rows mirroring `MyTicketsPreview`'s skeleton.

The widget refetches on a 60-second interval (matching the existing dashboard query convention if there is one — check `MyTicketsPreview.tsx`) plus on focus.

## Patterns and conventions

- Match the visual cadence of `<MyTicketsPreview>` for the new widget — same header style, same row density, same skeleton pattern.
- Use `data-testid` consistently: `data-testid="widget-my-batches"`, `data-testid="widget-my-batches-row-${campaignId}"`, `data-testid="page-my-batches"`, `data-testid="my-batches-search"`, etc.
- All user-facing strings via i18next, both `en.ts` and `es.ts`.
- The `/api/me/extra-billable-batches` endpoint should be a single query (with joins/aggregates) — N+1 is unacceptable for a dashboard widget that fires every 60 seconds for every field user.
- Use existing `useToast` for any error states.
- Use `lucide-react` for all icons — likely `<ClipboardList>` for the batch concept, `<Users>` for empty state.
