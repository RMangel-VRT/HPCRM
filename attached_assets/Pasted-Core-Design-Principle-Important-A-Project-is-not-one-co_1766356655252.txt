Core Design Principle (Important)

A Project is not one continuous ticket with the same owner.

It has three distinct phases:

Sales / Estimating (Office-owned)

Execution (Ops-owned)

Billing (Office-owned)

Trying to force all three into one long workflow with the same ticket causes friction.
Instead, we use intentional ticket transitions + spawning.

Revised Project Ticket Model (Recommended)
Ticket Types Involved

Project Ticket (sales + approval tracking)

Execution Task Ticket (crew-facing, ops-owned)

Invoice Ticket (office-facing, billing)

Each ticket has a clear owner and clear purpose.

Revised Project Ticket Workflow (Office-Owned)
Step 1 — New (Request Created)

Purpose: Capture the request.

Created by Admin / Office

Fields:

Customer

Project description

Requested scope

Photos / location (if available)

✔ No required fields beyond description.

Step 2 — Estimating

Purpose: Reference the estimate built in QuickBooks.

Estimating does not happen inside this system.

Required to advance:

QuickBooks Estimate Number (text field)

Optional notes

✔ Once estimate number is attached → move forward

Step 3 — Estimate Sent

Purpose: Track that pricing has been sent.

Required to advance:

Date estimate sent

Delivery method (email / QBO / portal)

✔ Waiting stage — no ops involvement yet

Step 4 — Decision Received

Purpose: Approval gate.

Required:

Decision:

❌ Denied → Close Project Ticket (Closed – Lost)

✅ Approved → Continue

If Denied:

Capture reason (optional)

Ticket closes

If Approved:

Approval date

PO number (optional)

✔ Approval triggers the handoff to operations

Handoff Point (This Is the Key Change)

At approval:

System Action (Prompted, not silent)

“This project is approved. Create execution task for the field?”

Yes → Create new ticket:

Ticket Type: Execution Task (or Onsite Maintenance Task / Project Execution Task)

Linked to: Project Ticket

Ownership: Crew Leader / Ops

Includes:

Scope summary

Location

Photos

Notes

Target completion window

The Project Ticket pauses here and becomes read-only until execution completes.

Execution Task Ticket (Crew-Owned)

This is what the crew actually works from.

Execution Task Flow (Simpler)

Scheduled

Scheduled date

Crew size

In Progress

Actual start date

Completed

Completion date

Actual hours

Completion photos

Notes

✔ Once marked Completed, control returns to Admin.

Return to Project Ticket (Office-Owned Again)
Step 5 — Work Completed (Auto or Manual)

Triggered when linked Execution Task is completed.

Shows:

Completion date

Actual hours (read-only summary)

Completion photos (read-only)

Step 6 — Ready for Billing

Purpose: Explicit billing checkpoint.

Required to advance:

Confirmation checkbox:

“Work complete and ready for invoicing”

✔ This creates or prompts creation of an Invoice Ticket

Step 7 — Invoicing (Final)

Purpose: Track billing without mixing with ops.

Required:

QuickBooks Invoice Number

Invoice amount

Invoice date

✔ Project Ticket closes as Closed – Completed

Why This Is Better Than the Current 8-Step Flow
What You Gain

Clear ownership shifts (Office → Ops → Office)

Crews never see estimating/billing steps

Office never manages execution statuses manually

Clean audit trail:

Project approved → work done → invoice sent

Matches how QuickBooks is actually used

What You Avoid

One ticket being “owned by everyone”

Ops touching billing fields

Admin tracking start/stop times manually

Confusing step overload
