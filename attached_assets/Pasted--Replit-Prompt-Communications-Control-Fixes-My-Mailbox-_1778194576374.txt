# Replit Prompt — Communications Control Fixes (My Mailbox Backfill + Inbox/Sent Delete + Sorted Badges + Seed Cleanup)

## Context

After porting the Communications Rework into the live workspace, three concrete gaps remain that are making the system feel uncontrollable:

1. The **"Manage backfill" button on My Mailbox is a stubbed disabled button** (tooltip says "available in a future update"). The underlying `BackfillPanel` component, the `/api/mailbox-accounts/:id/backfill` endpoints, and the role check that allows personal-mailbox owners are all already built and shipping. The button just was never wired up.
2. The **Inbox/Sent/All tabs have no row-level delete affordance**. The server's `DELETE /api/communications/:id` endpoint exists but is gated behind the `manage_automations` permission (`admin` only), and no UI calls it. Result: there's no way to remove the seed sample emails (`Spring Service Schedule Confirmation`, `Crew arriving today`, `Customer Meeting Notes`, `Summer Services Proposal Follow-Up`, `Annual Contract Renewal Notice`, `Monthly Service Report - March 2026`, `Service cancellation notice`) inserted by `seedCommunicationsBootstrap` on first server start, or to delete any test/garbage row that a user has decided is wrong.
3. The **Inbox tab shows the customer name as small grey text after the from-address** but never makes it visually clear when an email has been correctly linked to a customer vs. is unsorted vs. was hand-routed through the Unsorted queue. There's no at-a-glance "this is sorted" feedback.

This prompt closes all three. It is mostly mechanical wiring — every piece of backend it depends on already exists.

This must land in a deployable, production-quality state. No stubs, no `// TODO` comments hiding incomplete code paths.

### 2b. Build a reusable DeleteCommunicationButton component

Create `artifacts/highplains-crm/src/components/customer/communications/DeleteCommunicationButton.tsx`:

```tsx
import { useState } from "react";
import { useMutation } from "@tanstack/react-query";
import { Trash2, Loader2 } from "lucide-react";
import {
  AlertDialog,
  AlertDialogAction,
  AlertDialogCancel,
  AlertDialogContent,
  AlertDialogDescription,
  AlertDialogFooter,
  AlertDialogHeader,
  AlertDialogTitle,
  AlertDialogTrigger,
} from "@/components/ui/alert-dialog";
import { Button } from "@/components/ui/button";
import { apiRequest, queryClient } from "@/lib/queryClient";
import { useToast } from "@/hooks/use-toast";

interface DeleteCommunicationButtonProps {
  communicationId: string;
  subject?: string | null;
  /** Query keys to invalidate after a successful delete. */
  invalidateKeys?: unknown[][];
  /** Optional callback after success (e.g. close a modal). */
  onDeleted?: () => void;
  /** Variant for icon-only inline use vs. labeled button. */
  size?: "icon" | "sm";
}

export default function DeleteCommunicationButton({
  communicationId,
  subject,
  invalidateKeys = [],
  onDeleted,
  size = "icon",
}: DeleteCommunicationButtonProps) {
  const { toast } = useToast();
  const [open, setOpen] = useState(false);

  const mutation = useMutation({
    mutationFn: async () => {
      const res = await apiRequest("DELETE", `/api/communications/${communicationId}`);
      if (!res.ok && res.status !== 204) {
        const text = await res.text().catch(() => "");
        throw new Error(text || "Failed to delete");
      }
    },
    onSuccess: () => {
      toast({ title: "Communication deleted" });
      invalidateKeys.forEach(k => queryClient.invalidateQueries({ queryKey: k }));
      // Always invalidate the canonical list and count keys.
      queryClient.invalidateQueries({ queryKey: ["/api/communications"] });
      setOpen(false);
      onDeleted?.();
    },
    onError: (err: Error) => {
      toast({
        title: "Failed to delete",
        description: err.message,
        variant: "destructive",
      });
    },
  });

  return (
    <AlertDialog open={open} onOpenChange={setOpen}>
      <AlertDialogTrigger asChild>
        <Button
          variant="ghost"
          size={size === "icon" ? "icon" : "sm"}
          className={size === "icon" ? "h-7 w-7 shrink-0 text-muted-foreground hover:text-destructive" : "gap-1.5 text-destructive"}
          onClick={(e) => { e.stopPropagation(); /* don't trigger row click */ }}
          data-testid={`button-delete-communication-${communicationId}`}
          aria-label="Delete communication"
        >
          {mutation.isPending ? <Loader2 className="w-4 h-4 animate-spin" /> : <Trash2 className="w-4 h-4" />}
          {size === "sm" && <span>Delete</span>}
        </Button>
      </AlertDialogTrigger>
      <AlertDialogContent onClick={(e) => e.stopPropagation()}>
        <AlertDialogHeader>
          <AlertDialogTitle>Delete this communication?</AlertDialogTitle>
          <AlertDialogDescription>
            {subject
              ? <>The message <span className="font-medium">"{subject}"</span> will be permanently removed. This cannot be undone.</>
              : "This message will be permanently removed. This cannot be undone."}
          </AlertDialogDescription>
        </AlertDialogHeader>
        <AlertDialogFooter>
          <AlertDialogCancel data-testid="button-delete-cancel">Cancel</AlertDialogCancel>
          <AlertDialogAction
            onClick={() => mutation.mutate()}
            disabled={mutation.isPending}
            data-testid="button-delete-confirm"
            className="bg-destructive text-destructive-foreground hover:bg-destructive/90"
          >
            {mutation.isPending ? "Deleting…" : "Delete"}
          </AlertDialogAction>
        </AlertDialogFooter>
      </AlertDialogContent>
    </AlertDialog>
  );
}
```

The `e.stopPropagation()` on the button and dialog content is essential — Inbox/Sent rows are themselves `<button>` elements that open `CommunicationsQuickViewModal` on click, so without it the modal opens behind the confirm dialog.

## Step 4 — Sorted badges on Inbox emails

Goal: at a glance, every Inbox row shows whether it has been linked to a customer and how. Three states:

- **Auto-sorted** (green badge `Sorted → {customerName}`) — the email sync service matched a customer at ingest time.
- **Manually sorted** (amber badge `Routed by {userName} → {customerName}`) — the email landed in Unsorted and a user routed it.
- **No customer link** (no badge) — should be rare in Inbox since unmatched mail goes to Unsorted, but possible if the customer was deleted after routing.

The data model already supports this distinction. `unsorted_emails.resolvedToCommunicationId` is the link from a triaged unsorted email to the resulting communications row. If a communication's `id` appears as a `resolvedToCommunicationId` somewhere, it was manually sorted.

### 4a. Extend the API response shape

In `artifacts/highplains-crm/src/shared/schema.ts`, extend `CommunicationWithDetails` (line 2815):

```ts
export type CommunicationWithDetails = Communication & {
  customerName?: string | null;
  contactName?: string | null;
  sentByName?: string | null;
  createdByName?: string | null;
  templateName?: string | null;
  isOverdue?: boolean;
  replyCount?: number;
  threadSubjectRoot?: string;
  scheduledFor?: Date | string | null;
  followUpDueAt?: Date | string | null;
  followUpStatus?: string | null;
  /** True if this communication was created by routing an unsorted email. */
  wasManuallySorted?: boolean;
  /** Display name of the user who routed it, if `wasManuallySorted`. */
  manuallySortedByName?: string | null;
};
```

### 4b. Populate it in the storage layer

`artifacts/api-server/src/storage.ts:3841` (`getCommunications`) is the function backing `GET /api/communications`. After the main rows are fetched, do a single LEFT JOIN against `unsortedEmails` to find which communication ids were resolved from an unsorted email and who resolved them.

Sketch (adapt to the file's existing query style — don't rewrite the whole function):

```ts
// After loading `rows: CommunicationWithDetails[]`:
const resolvedRows = rows.length === 0 ? [] : await db
  .select({
    communicationId: unsortedEmails.resolvedToCommunicationId,
    resolverName: users.name,
  })
  .from(unsortedEmails)
  .leftJoin(users, eq(unsortedEmails.resolvedByUserId, users.id))
  .where(and(
    eq(unsortedEmails.companyId, companyId),
    inArray(unsortedEmails.resolvedToCommunicationId, rows.map(r => r.id)),
  ));

const resolvedMap = new Map(resolvedRows.map(r => [r.communicationId!, r.resolverName ?? null]));

return rows.map(r => ({
  ...r,
  wasManuallySorted: resolvedMap.has(r.id),
  manuallySortedByName: resolvedMap.get(r.id) ?? null,
}));
```

Imports needed at the top of `storage.ts` (most are already there): `inArray` from `drizzle-orm`, `unsortedEmails` and `users` from `@workspace/db`.

Mirror the same enrichment in `getCommunicationById` (or whatever the single-row getter is) so the QuickViewModal also sees the badge fields. If there's a separate `getCommunicationsForCustomer` used by the modal's `["/api/customers", customerId, "communications", "recent"]` query, extend that too.

## Things to NOT change in this slice

- `seedCommunications` and `seedCommunicationsBootstrap` — leave the seed function in place; the goal is to give the user an explicit way to clear it, not to delete the seed mechanism (it's still useful for fresh demos).
- Backfill backend routes — no schema or auth changes; the existing setup already permits self-serve.
- Unsorted tab — it already has route/archive/spam actions and doesn't need a separate delete affordance for this slice. (`archive` is the soft delete for unsorted_emails.)

- Drizzle schema — no migrations; `unsortedEmails.resolvedToCommunicationId` and `resolvedByUserId` already exist.
- The Comms shell, secondary nav, or routing — they shipped clean in the previous port.

## Why this exists

After the multi-artifact restructure and the four Comms Rework slices, the user-facing controls felt asymmetric: connection works, sync works, browsing works, but the single most basic CRUD verb — **delete** — was never wired into the UI, the backfill UI on per-user My Mailbox was a stub, and the Inbox didn't communicate routing state visually. This slice closes those three gaps so admin/office users feel in control of their own communications surface.
