# Chemical Campaign Communication — Analysis & Replit Slices

> Single combined document: root-cause analysis followed by paste-ready Replit prompts
> ("slices"). Run Slices 1–3 in order (the actual send bug + tests); Slice 4 is the
> optional UX safeguard.

---

## 1. Symptom

Chemical campaign emails send the **template defaults only** — per-visit variable
changes and (apparently) template edits don't show up in the sent email.

---

## 2. What's actually correct (verified — do NOT touch)

- Template create / PATCH save — `routes.ts` `/api/chemical-notification-templates`
  + `storage.updateChemicalNotificationTemplate` write all fields. ✅
- Campaign template selection save — create (`routes.ts` ~L13328) and PATCH
  (~L13837) persist `notificationTemplateId`. ✅
- `storage.getCampaignById` uses `db.select()` (all columns) — returns
  `notificationTemplateId`. ✅
- `renderChemicalNotificationTemplate` (`emailService.ts` ~L765) correctly layers
  template metadata as defaults, with non-empty caller vars overriding. ✅
- Template edit form `ChemicalNotificationTemplates.tsx` (`handleEdit`, create/update
  mutations) sends all fields. ✅

The save/render plumbing is fine. The defect is in the **send actions**.

---

## 3. Bug #1 — per-visit overrides dropped in pre/post send (the real defect)

`artifacts/api-server/src/routes/routes.ts` has three chem send actions:

| Action | Location | Builds vars via | Includes per-visit overrides? |
|---|---|---|---|
| `send_notification` | ~L14596 | `buildChemicalNotificationVariables(...)` | ✅ yes |
| `send_pre_communication` | ~L14453 | **inline object** (L14457–14472) | ❌ no |
| `send_post_communication` | ~L14545 | **inline object** (L14549–14564) | ❌ no |

The pre/post inline objects never pass `purpose`, `reentryInterval`,
`wateringInstructions`, or `mowingInstructions`, even though the handler destructures
`purposeOverride`, `reentryIntervalOverride`, `wateringInstructionsOverride`,
`mowingInstructionsOverride` from the request. Result: the renderer always uses
template defaults → "not variable changes."

**Decision (Randy):** per-visit overrides SHOULD flow into pre/post emails.

---

## 4. Bug #2 — "not template changes" is a data-linkage gap, not a code bug

When `campaign.notificationTemplateId` is null, `resolveChemicalNotificationTemplate`
(`emailService.ts` ~L740) falls back to the company `isDefault` template. So editing a
**non-default** template appears to do nothing because the campaign is silently using
the default. Fix is UX/linkage, not the render path. See Slice 4.

---

## 5. Fix plan

- **Slice 1** — add overrides to `send_pre_communication` vars.
- **Slice 2** — add overrides to `send_post_communication` vars.
- **Slice 3** — tests proving overrides + template edits apply.
- **Slice 4** (optional) — template-linking safeguard for Bug #2.

## Slice 1 — Fix pre-communication send (per-visit overrides)

**File:** `artifacts/api-server/src/routes/routes.ts`
**Action:** `send_pre_communication` (around line 14453)

### Prompt for Replit

> In `artifacts/api-server/src/routes/routes.ts`, in the `send_pre_communication`
> chem action (around line 14453), the inline `vars` object passed to
> `renderChemicalNotificationTemplate(campaign, user.activeCompanyId, 'pre', {...})`
> is missing the per-visit override fields. The handler already destructures these
> from `targetItem` but never forwards them, so the renderer always uses template
> defaults.
>
> Add these keys to that inline `vars` object, derived from `targetItem`, only when
> non-empty (pass `''` or omit otherwise — the renderer treats empty caller vars as
> "use template default", so empty values must not clobber):
>
> - `purpose`: `targetItem.purposeOverride`
> - `reentryInterval`: `String(targetItem.reentryIntervalOverride)` — it's a number;
>   convert to string, skip if null/undefined
> - `wateringInstructions`: `targetItem.wateringInstructionsOverride`
> - `mowingInstructions`: `targetItem.mowingInstructionsOverride`
>
> Do not change any other behavior in this handler (recipient resolution, label
> attachment, applicator, workflow step updates, audit log all stay as-is).

### Acceptance
- Sending a pre-communication for an item with per-visit overrides produces an email
  whose subject/HTML reflect the override values.
- An item with no overrides still renders the template's stored defaults.

## Slice 4 — Template-linking safeguard (optional, addresses "not template changes")

**Files:** campaign create/edit UI + `CampaignDetail` page (frontend); no server render
changes needed.

### Background
When a campaign's `notificationTemplateId` is null, the server
(`resolveChemicalNotificationTemplate`, `emailService.ts` ~L740) falls back to the
company's `isDefault` chemical notification template. So a user who edits a
**non-default** template sees "nothing changed" because the campaign is silently using
the default template.

### Prompt for Replit

> Investigate why chemical campaigns can end up with `notificationTemplateId = null`,
> then implement the lower-risk of these two options (recommend #2 unless data shows
> otherwise):
>
> 1. **Require explicit selection:** in the chemical campaign create/edit form, require
>    an explicit notification-template choice instead of defaulting to "default".
> 2. **Surface the active template:** on the campaign detail page, clearly display which
>    notification template the campaign is actually using (including when it's the
>    company default), so users don't edit the wrong template.

### Acceptance
- A user can tell, from the campaign, exactly which template its emails will use.
- (If option 1) chemical campaigns can't be saved without a template selection.

### Priority
Lower than Slices 1–3. Do the send-path fix first; this closes the "edited the wrong
template" UX gap.
