# P3-2: Visits (one crew, one day, one trip)

> Assumes 00-RULES-P3.md and P3-1 merged and published. **Line numbers are from GitHub `683a109`**; find code by its content. **Schema: one new table, additive.** Use the **next free migration number** (0046 at the time of writing; Contract Center work also adds migrations, so check first).
>
> The risk here: two sources of truth for "when is this job happening". Visits become the source. The ticket's `crew_id` / `due_date` / `route_order` become a **mirror** that one function maintains, so the crew app's Today keeps working unchanged. No UI in this slice except what the tests need; the board is P3-3.

## Facts (verified at 683a109)

- **The crew app's Today** (`GET /api/m/today`, crewsAndMobile.ts ~L370, plus the copy ~L1917) reads `tickets` where:
  - `crew_id` = the supervisor's crew (`resolveSupervisorCrewId`);
  - `due_date` falls in `companyDayBounds(date)`;
  - ordered by `route_order` nulls last, then `due_date`.
- **`tickets.due_date` is a timestamp.** The web client writes it as **noon local** (TicketDetail ~L1057). `due_date` alone also serves as a plain deadline on tickets with no crew (To-Dos, estimates), so **only a crew + due date pair means a crew trip.**
- **Phase 2's crew + date rule** lives inline in `PATCH /api/tickets/:id` (routes.ts ~L6818–6838):
  - `ready_to_schedule` + crew + date → `scheduled`, with the note "Crew and date set";
  - `scheduled` losing its crew or date → `ready_to_schedule`, with "Crew or date cleared".
- **Production has no standing crews until Randy creates them** after the P3-1 publish. So no existing ticket has a `crew_id` in production. The backfill (§4) will very likely find nothing; that's expected.
- **Tickets have no estimated-hours field.** Visits carry their own, optional.

## 1. Schema: `visits`

```sql
CREATE TABLE IF NOT EXISTS visits (
  id varchar PRIMARY KEY DEFAULT gen_random_uuid(),
  company_id varchar NOT NULL REFERENCES companies(id) ON DELETE CASCADE,
  crew_id varchar REFERENCES crews(id) ON DELETE SET NULL,
  visit_date date NOT NULL,                       -- Colorado calendar date
  source_type text NOT NULL DEFAULT 'ticket',     -- 'ticket' | 'internal' now; 'maintenance' | 'campaign_item' in Phase 5
  ticket_id varchar REFERENCES tickets(id) ON DELETE CASCADE,
  customer_id varchar REFERENCES customers(id) ON DELETE SET NULL,
  title text,                                     -- for internal visits with no ticket
  route_order integer,
  start_time text,                                -- optional HH:MM
  estimated_hours real,
  status text NOT NULL DEFAULT 'planned',         -- planned | in_progress | done | skipped | cancelled
  actual_start_at timestamp,
  actual_end_at timestamp,
  notes text,
  created_by_id varchar REFERENCES users(id) ON DELETE SET NULL,
  created_at timestamp NOT NULL DEFAULT now(),
  updated_at timestamp NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS visits_company_date_crew_idx ON visits (company_id, visit_date, crew_id);
CREATE INDEX IF NOT EXISTS visits_ticket_idx ON visits (ticket_id);
CREATE INDEX IF NOT EXISTS visits_company_customer_date_idx ON visits (company_id, customer_id, visit_date);
```

- Mirror it in `schema.ts` with a zod insert schema: `visitDate` matches `YYYY-MM-DD`, `startTime` matches `HH:MM`, `estimatedHours` is 0–24, and `status` / `sourceType` are enums. Add it to the client schema copy too.
- **`customer_id` is copied from the ticket** on create, so property pages (Phase 5) can read visits without joining tickets.
- **`ticket_id` is required when `source_type = 'ticket'`**, and `title` is required for `'internal'`. Enforce both in zod.

## 2. One function keeps the ticket in step: `lib/visitSync.ts`

```ts
/** Recompute a ticket's crew/date/route mirror from its visits, then apply the Phase 2 status rule. */
export async function syncTicketFromVisits(ticketId: string, companyId: string, actingUserId: string, tx?): Promise<SyncResult>
```

- **Which visit wins:** among the ticket's visits with status `planned` or `in_progress`, take the **earliest `visit_date` on or after Colorado today**. If none qualifies, take the latest one before today.
- **With a winning visit:**
  - `crew_id` = the visit's crew;
  - `due_date` = **12:00 America/Denver** on its `visit_date` (matching the web client's noon convention, so Today's day window and every date display agree);
  - `route_order` = the visit's route order.
- **With no open visit:** clear `crew_id` and `route_order`. **Leave `due_date` alone**, because it may be a real deadline.
- **Status:** apply the Phase 2 rule through **one extracted helper**, `applySchedulingTransition(updates, existing, statuses)`.
  - Move the inline block from `PATCH /api/tickets/:id` into this helper. PATCH and visit sync both call it, so the rule lives in one place.
  - Keep the "explicit status intent wins" guard exactly as it is.
  - Write status history and the notes exactly as PATCH does today.
- Only write the ticket when something actually changed. Do it in the caller's transaction.

**Use `syncTicketFromVisits` after every visit create, move, status change or delete.** Nothing else writes those three ticket fields for a ticket that has visits (see §3c).

## 3. API (new `routes/visits.ts`, registered from `registerRoutes`)

**Who can call it:**
- **Read:** admin, office and field_manager.
- **Write:** admin, office and field_manager.

Everyone else gets 403. Field managers see and schedule every crew in Phase 3; per-crew limits come later if Randy wants them.

### 3a. Reads

- **`GET /api/visits?from=YYYY-MM-DD&to=YYYY-MM-DD[&crewId][&customerId][&ticketId]`**
  - `from`/`to` are Colorado dates, inclusive, at most 62 days apart (400 otherwise).
  - Returns visits ordered by date, crew display order, route order, then start time.
  - Each row is enriched in bulk with:
    - `ticket: { id, title, typeKey, typeName, statusKey, statusName, priority, scheduleBy }`;
    - `customer: { id, name }`;
    - `crew: { id, name, color }`.
  - Missing or foreign counterparts become `null`, never another company's data.
- **`GET /api/visits/summary?from&to`:** one row per crew per day, `{ crewId, date, visitCount, plannedHours, capacityHours }`.
  - `plannedHours` sums the visits' `estimated_hours`; a visit with no hours counts 0.
  - `capacityHours` is the crew's `default_hours_per_day`, or 8.
  - Count `planned` and `in_progress` visits only.
  - One grouped query.

### 3b. Writes

- **`POST /api/visits`** takes `{ ticketId?, crewId, visitDate, routeOrder?, startTime?, estimatedHours?, notes?, title? }`.
  - The crew must be an **active** standing crew in this company (400 otherwise).
  - **A ticket visit is rejected (422 `NOT_SCHEDULABLE`)** unless the ticket is in this company, not in a final status, and its type has a stable `scheduled` status. That means Task, Project and Estimate Request; To-Do and Invoice are rejected.
  - If `routeOrder` is omitted, append it to the end of that crew's day.
  - Then sync the ticket. Return the visit plus `ticketSync: { statusChanged, newStatusKey }` so the board can show "Moved to Scheduled".
- **`PATCH /api/visits/:id`** (uses `pickProvided`) can change `crewId`, `visitDate`, `routeOrder`, `startTime`, `estimatedHours`, `notes` and `status`.
  - Changing the crew or date appends the visit to the end of the new day unless `routeOrder` is given.
  - A `done`, `skipped` or `cancelled` visit can't be moved (409 `VISIT_CLOSED`).
  - Sync afterwards.
- **`DELETE /api/visits/:id`:** only `planned` visits can be deleted (409 otherwise; the caller should cancel instead). Sync afterwards.
- **`POST /api/visits/reorder`** takes `{ crewId, visitDate, visitIds[] }`.
  - `visitIds` must be exactly that crew's open visits for that day (400 otherwise).
  - Write route order 1…n in one transaction, then sync each affected ticket.

**Concurrency:** every write runs in a transaction and locks the ticket row (`FOR UPDATE`) when there is one, so two people dragging the same job can't leave its mirror out of step.

### 3c. Existing ticket edits stay compatible

In `PATCH /api/tickets/:id`, when the body sets `crewId` or `dueDate` on a ticket whose type has a `scheduled` status:

| The ticket has… | Behavior |
|---|---|
| No open visits, and a crew + date result | Create one visit from them, then sync |
| Exactly one open visit | Move that visit to the new crew/date, or delete it if the crew is cleared, then sync |
| Two or more open visits | **409 `MULTIPLE_VISITS`**: "This job has several visits. Change them on the schedule." |

- If only `dueDate` is set on a ticket with no crew, that's a deadline: no visit, and behavior as today.
- Ticket types without a `scheduled` status (To-Do, Invoice, …) behave exactly as today.
- Mobile endpoints don't write crew or date. Confirm that, and report anything that does.

## 4. Backfill (guarded, idempotent, DML only)

`backfillVisitsFromTickets()`, called once from `registerRoutes` after `linkCrews`, only when the `visits` table exists.

- For every **non-final** ticket with `crew_id` and `due_date` set **and no visits yet**:
  - create one `planned` visit;
  - `visit_date` = `companyDateString(due_date)`;
  - copy the crew, route order and customer;
  - `source_type = 'ticket'`.
- Don't touch the ticket's fields or status.
- Log `[backfillVisits] company=… created=N`.
- A second run creates nothing.

**Read-only production check (report it at the top):** count the non-final tickets that have both `crew_id` and `due_date`. It is expected to be 0 or close to it until Randy creates crews.

## Tests (run under `TZ=UTC` and `TZ=America/Denver`)

- **Sync:**
  - creating a visit for a Needs scheduling Task sets crew, due date (noon Colorado on that date) and route order, and moves it to Scheduled with history;
  - deleting its only visit clears crew and route order, keeps the due date, and moves it back to Needs scheduling;
  - with two visits (yesterday's done, next Tuesday's planned), the mirror points at Tuesday;
  - with an In progress ticket, adding or removing visits never changes its status.
- **Today stays correct:** at 8 pm Colorado time under `TZ=UTC`, a visit placed for today appears in `GET /api/m/today` for that crew's supervisor, and tomorrow's doesn't.
- **Validation:**
  - To-Do and Invoice tickets are rejected with 422;
  - a final-status ticket is rejected with 422;
  - an inactive or foreign crew is rejected with 400;
  - a range over 62 days is rejected with 400;
  - moving a done visit gives 409;
  - deleting a non-planned visit gives 409;
  - reorder with a wrong ID set gives 400.
- **Ticket PATCH compatibility:**
  - crew + date on a ticket with no visit creates one;
  - with one visit, it moves it;
  - with two visits, it returns 409;
  - a date only, with no crew, creates no visit;
  - a To-Do behaves exactly as before.
- **Concurrency:** two parallel moves of the same ticket's visit leave the mirror matching the final visit.
- **Backfill:** creates one visit per qualifying ticket, skips tickets that already have visits, and a rerun creates zero.
- **Reads:**
  - foreign counterparts come back as null;
  - the query count doesn't grow with the number of rows;
  - the summary sums hours and falls back to 8 hours of capacity.
