# P1-1: Task type on the server

> Assumes 00-RULES.md and P0-1 merged. The risk here: the one-time conversion must run **exactly once**. If it ran every boot, it would flip every contract Task back to billable on each restart.

## What changes

The Extra Billable ticket type row becomes **Task**. It keeps its id, its statuses (and their status keys), its fields, and every ticket and history row. Only its name, its `type_key` (`extra_billable` → `task`), its description and its capability flags change. Task holds both contract and billable field work. Whether a Task gets invoiced is decided **per ticket** (P1-2), so the Task type's `requires_invoicing` is `false`.

Status names don't change in this slice. Phase 2 renames "Ready to Schedule" and adds "Scheduled."

## 1. Identity: `shared/ticketCapabilities.ts` + `lib/db/src/schema/schema.ts`

- `lib/db/src/schema/schema.ts`: in `TicketTypeKey`, replace `"extra_billable"` with `"task"`. In the `typeKey` zod enum on the ticket-type insert schema (~L629), do the same.
- `TICKET_TYPE_NAMES_BY_KEY`: replace `extra_billable: "Extra Billable"` with `task: "Task"`.
- `LEGACY_TICKET_TYPE_NAME_ALIASES`: add `task: ["Extra Billable"]`. An unkeyed row still named "Extra Billable" then resolves as Task through the existing fallback path.
- `TICKET_TYPE_CAPABILITIES`: replace the `"Extra Billable"` entry with:
  ```ts
  "Task": {
    requiresCustomer: "true",
    requiresScheduling: "true",
    requiresCompletion: "true",
    requiresInvoicing: "false",   // decided per ticket by billingBehavior — see P1-2
    terminalBehavior: "close",
  },
  ```
- `STATUS_KEY_BACKFILL`: rename the `"Extra Billable"` key to `"Task"`. Keep the same status names and keys: `new`, `ready_to_schedule`, `in_progress`, `work_completed`, `ready_for_billing`, `closed_won`.
- `TICKET_TYPE_KEYS` is derived from `TICKET_TYPE_NAMES_BY_KEY`, so it updates on its own.

## 2. One-time conversion: new `migrateExtraBillableToTask()` in routes.ts

Call it in `registerRoutes()` **after** `migrateTicketTypeRename()` and **before** `backfillTicketTypeCapabilities()`.

For each company:

1. Find the row with `type_key = 'extra_billable'`, or if there's none, the row with `type_key IS NULL AND name = 'Extra Billable'`. **If there's no such row, do nothing.** That's what makes it one-time: after the first run no row matches.
2. If the company **already has** a row with `type_key = 'task'`, log a warning and skip that company. Don't merge.
3. Otherwise, in one `db.transaction`:
   ```sql
   UPDATE tickets SET work_type = 'extra_work', billing_behavior = 'invoice_required', updated_at = now()
     WHERE ticket_type_id = $ebTypeId;
   UPDATE ticket_types SET name = 'Task', type_key = 'task',
     description = 'Field work for a crew: contract or billable. Billable tasks create a linked invoice ticket.'
     WHERE id = $ebTypeId;
   ```
   Every existing Extra Billable ticket becomes a billable Task. Randy approved this. It also repairs the tickets the old save bug had reset to contract / no invoice.
4. Log the per-company ticket count.

Don't touch `mobile_status`, `priority`, statuses or history.

  - Inside the helper: `statusMap.get("Work Completed")` → `.get("work_completed")`.
  - Grep for any other `.statuses.get(` on this helper's return value.
- Don't change the other `ensure*` helpers in this slice.
