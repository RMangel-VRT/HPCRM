# Replit Slice A — Ticket type capability flags + stable status keys

**Ships dark. Zero behavior change. No reader is allowed to change in this slice.**

## Why

Right now the app decides what a ticket can do by string-matching the ticket type's *display name* — `ticketType.name === "Extra Billable"` — in 76 places, plus 14 more matching on status display names. That is why renaming a ticket type required a dedicated repair migration (`migrateTicketTypeRename`). This slice adds the data those checks should be reading, and backfills it. It changes nothing about how the app behaves today.

A later slice migrates the readers. **Do not migrate any readers in this slice.**

## 2. Startup migration — `artifacts/api-server/src/routes/routes.ts`

Add one exported function. Follow the existing house pattern exactly (see `migrateUserPhoneColumn` / `migrateEquipmentProfilePhotoColumn` in the same file): raw SQL, `IF NOT EXISTS`, wrapped in try/catch, logs on both paths, never throws.

```ts
/**
 * Slice A: add ticket-type capability flags and stable status keys, then backfill
 * them for every existing company from the known seeded workflows.
 *
 * Idempotent — safe to run on every boot. Backfill only ever writes a row whose
 * value is still NULL/default, so a hand-edited value is never clobbered.
 *
 * NOTHING READS THESE COLUMNS YET. This migration is deliberately inert.
 */
export async function migrateTicketTypeCapabilities(): Promise<void> {
  console.log("Running startup migration: ticket type capability flags + status keys...");
  try {
    // ── columns ──────────────────────────────────────────────────────────────
    await db.execute(sql`ALTER TABLE ticket_types ADD COLUMN IF NOT EXISTS requires_customer   text NOT NULL DEFAULT 'true'`);
    await db.execute(sql`ALTER TABLE ticket_types ADD COLUMN IF NOT EXISTS requires_scheduling text NOT NULL DEFAULT 'false'`);
    await db.execute(sql`ALTER TABLE ticket_types ADD COLUMN IF NOT EXISTS requires_completion text NOT NULL DEFAULT 'false'`);
    await db.execute(sql`ALTER TABLE ticket_types ADD COLUMN IF NOT EXISTS requires_invoicing  text NOT NULL DEFAULT 'false'`);
    await db.execute(sql`ALTER TABLE ticket_types ADD COLUMN IF NOT EXISTS terminal_behavior   text NOT NULL DEFAULT 'close'`);
    await db.execute(sql`ALTER TABLE ticket_type_statuses ADD COLUMN IF NOT EXISTS status_key text`);
    await db.execute(sql`CREATE INDEX IF NOT EXISTS ticket_type_statuses_key_idx ON ticket_type_statuses (ticket_type_id, status_key)`);

    // ── backfill capability flags by seeded type name ────────────────────────
    // Matching on name here is correct and intentional: this is the ONE place
    // that translates the old name-based world into the new flag-based one.
    for (const [name, f] of Object.entries(TICKET_TYPE_CAPABILITIES)) {
      await db.execute(sql`
        UPDATE ticket_types
        SET requires_customer   = ${f.requiresCustomer},
            requires_scheduling = ${f.requiresScheduling},
            requires_completion = ${f.requiresCompletion},
            requires_invoicing  = ${f.requiresInvoicing},
            terminal_behavior   = ${f.terminalBehavior}
        WHERE name = ${name}
      `);
    }

    // ── backfill status keys by (type name, status name) ─────────────────────
    let keyed = 0;
    for (const [typeName, map] of Object.entries(STATUS_KEY_BACKFILL)) {
      for (const [statusName, key] of Object.entries(map)) {
        const r = await db.execute(sql`
          UPDATE ticket_type_statuses s
          SET status_key = ${key}
          FROM ticket_types t
          WHERE s.ticket_type_id = t.id
            AND t.name = ${typeName}
            AND s.name = ${statusName}
            AND s.status_key IS NULL
        `);
        keyed += (r as { rowCount?: number }).rowCount ?? 0;
      }
    }

    const unkeyed = await db.execute(sql`
      SELECT count(*)::int AS n FROM ticket_type_statuses WHERE status_key IS NULL
    `);
    console.log(
      `Ticket capability migration complete: ${keyed} status keys written, ` +
      `${(unkeyed as any).rows?.[0]?.n ?? "?"} statuses still unkeyed (expected for user-created custom statuses)`
    );
  } catch (error) {
    console.error("Error during ticket type capability migration:", error);
  }
}
```

## 4. Make new companies get the values too

**This is the step that is easiest to miss.** The migration only fixes companies that already exist. Every seeding helper in `routes.ts` that creates a ticket type or status must also set the new fields, or newly onboarded companies get defaults that are wrong.

Update each of these `ensure*` / seed helpers so their `storage.createTicketType({...})` call spreads the capabilities, and each `storage.createTicketTypeStatus({...})` call passes its `statusKey`:

| Helper | Approx. line | Type it seeds |
|---|---|---|
| `ensureInvoiceTicketType` | 236 | Invoice |
| `ensureRFPRequestTicketType` | 316 | RFP Request |
| `ensureEstimateRequestTicketType` | 535 | Estimate Request |
| `ensureExtraBillableTicketType` | 745 | Extra Billable |
| `ensureProjectTicketType` | 830 | Project |
| `ensureToDoTicketType` | 933 | To-Do |

Pattern for the type:

```ts
invoiceType = await storage.createTicketType({
  companyId,
  name: "Invoice",
  // …existing fields unchanged…
  ...TICKET_TYPE_CAPABILITIES["Invoice"],
});
```

Pattern for the statuses — each of these helpers builds its statuses from a local array literal of `{ name, description, color, order, isFinal, actionType }`. Add `statusKey` to each entry in those arrays, taking the value from `STATUS_KEY_BACKFILL`, and pass it through to `createTicketTypeStatus`.

`storage.createTicketType` (storage.ts L1828) and `storage.createTicketTypeStatus` (L1868) both pass the insert object straight through to Drizzle with no field whitelist, so **they need no change** — the new fields flow through automatically once the schema and the Zod insert schemas know about them.

All six helpers are module-private (`async function ensure…`, not exported), so the only callers are inside `routes.ts` — no other file needs touching.

## 6. Acceptance criteria

1. App boots cleanly; the migration logs `Ticket capability migration complete: N status keys written, M statuses still unkeyed`.
2. Running the app a second time logs `0 status keys written` (idempotent — the backfill only writes `WHERE status_key IS NULL`).
3. Every existing ticket still opens, and its status, badges, and workflow tab render exactly as before. **Nothing visual should change.**
4. These queries return the expected rows:

```sql
-- every seeded type has non-default flags where it should
SELECT name, requires_customer, requires_scheduling, requires_completion,
       requires_invoicing, terminal_behavior
FROM ticket_types ORDER BY name;

-- the three schedulable types, found by flag rather than by name
SELECT name FROM ticket_types WHERE requires_scheduling = 'true';
-- expect: Estimate Request, Extra Billable, Project

-- the three invoicing types
SELECT name FROM ticket_types WHERE requires_invoicing = 'true';
-- expect: Estimate Request, Extra Billable, Project

-- every seeded status is keyed; only user-created customs remain null
SELECT t.name AS type, s.name AS status, s.status_key
FROM ticket_type_statuses s JOIN ticket_types t ON t.id = s.ticket_type_id
WHERE s.status_key IS NULL ORDER BY t.name, s.display_order;

-- ready_for_billing is now findable across all three workflows at once
SELECT t.name, s.name FROM ticket_type_statuses s
JOIN ticket_types t ON t.id = s.ticket_type_id
WHERE s.status_key = 'ready_for_billing';
-- expect: Estimate Request, Extra Billable, Project
```

5. Create a brand-new test company and confirm its freshly seeded ticket types and statuses come out with the same flags and keys as an existing company's — this is what step 4 protects.
