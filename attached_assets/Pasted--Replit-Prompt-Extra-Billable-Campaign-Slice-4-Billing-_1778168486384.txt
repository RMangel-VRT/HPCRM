# Replit Prompt — Extra Billable Campaign, Slice 4: Billing Queue + Ticket Generation

## Context

This is **Slice 4 of 5** of the Extra Billable Campaign feature. Slices 1–3 added the schema, the crew assignment board, and the property grid with photo drop zones. Slice 4 closes the workflow: when the field work is done and crew leaders have marked properties complete with photos attached, the admin reviews the campaign and generates **Extra Billable tickets** in bulk — one ticket per completed property, photos attached, crew attribution set, all linked back to the campaign item for traceability.

The pattern is exactly the existing `POST /api/snow-events/:eventId/generate-tickets` flow at `server/routes.ts:9483` — but creates **Extra Billable** tickets (not Invoice tickets) at the **"Ready for Billing"** status. We skip the Execution states (New / Ready to Schedule / In Progress / Work Completed) because the campaign-side workflow already covered those — the photos and notes from the property assignment ARE the execution record.

The Slice 4 deployable end-state: an admin clicks "Billing Queue" tab on a finished extra_billable campaign, sees 47 completed-but-not-yet-billed properties listed, hits "Generate All Tickets," and watches 47 Extra Billable tickets appear at "Ready for Billing." Each ticket has the property's photos attached, the crew leader as `leadTechUserId`, all crew members in `crewMemberUserIds`, and the campaign item shows a link to its generated ticket. The existing ticket → invoice flow takes over from there.

This slice should land in a deployable, production-quality state. After it ships, the full storm-cleanup-to-billable-ticket loop is closed. Slice 5 (field crew leader polish) is independent and small.

## API endpoints

### 1. New: bulk ticket generation

```
POST /api/campaigns/:campaignId/generate-tickets
```

Body (optional):

```ts
{
  itemIds?: string[];   // explicit subset to generate; if omitted, generates for all eligible items
}
```

When `itemIds` is provided, validates every id belongs to this campaign and is eligible (see below); rejects with 400 + offending ids if any aren't. When omitted, the server picks up every eligible item.

Authentication required. **Admin or office role only** — return 403 for any other role.

Validation:

- Parent campaign exists for `user.activeCompanyId`. 404 otherwise.
- Campaign category is `"extra_billable"`. 400 otherwise — this endpoint is scoped.

Item eligibility (server-side filter — applied automatically when `itemIds` is omitted, validated against when provided):

- `status === "completed"` (skipped/pending items are not eligible)
- `billingStatus === "not_created"` (already-billed items are skipped silently — endpoint is idempotent)
- `assignedCampaignCrewId !== null` (items without a crew can't be billed because there's no leader to attribute the work)
- The assigned crew has a `leaderUserId` set (defensive — Slice 1 enforces this at assignment time, but verify on generation in case data drift happened)

Pre-flight ensures:

- `ensureExtraBillableTicketType(user.activeCompanyId)` is called first to guarantee the ticket type exists. Capture the returned `typeId` and `statuses` map.
- Look up the `"Ready for Billing"` status id from the map. If missing for any reason, return 500 with a clear error so an admin can investigate.

Per-item processing (mirror the snow-events loop pattern):

For each eligible item:

1. **Resolve crew details.** Fetch `campaign_crews` row for `assignedCampaignCrewId`, plus all `campaign_crew_members` for that crew. Capture: `leaderUserId`, `memberUserIds[]` (which already includes the leader since Slice 1's CRUD adds the leader to the members table). Also fetch the customer row to get the latest customer name and any service-address fields needed for the title.

2. **Build ticket title.** Format: `${campaign.title} — ${customerName}${customerCity ? " (" + customerCity + ")" : ""}`. Truncate at 200 characters if needed. Example: `"May 5 Spring Snow Branch Cleanup — Henderson Property Management (Lakewood)"`.

3. **Build ticket description.** Multi-line text, blank-line-separated sections (omit any section whose source value is empty):

   ```
   Source campaign: ${campaign.title}
   Campaign window: ${campaign.windowStart} – ${campaign.windowEnd}
   Crew: ${crew.name}
   Crew leader: ${leaderName}
   Crew members: ${memberNames.join(", ")}

   Photos: ${photos.length} attached

   Notes from the field:
   ${item.notes || "(none)"}

   ${item.estimatedAmount ? "Estimated: $" + item.estimatedAmount : ""}
   ```

   Use real newlines, not template-literal escapes. The existing snow-events endpoint at `:9517-9524` shows the join-with-newlines-and-filter-falsy pattern — use that.

4. **Copy photos via GCS server-side copy.** For each storage key in `item.photos[]`:

   - `srcPath = item.photos[i]` (already a full `extra-billable-photos/...` path)
   - `dstPath = "ticket-photos/" + companyId + "/" + ticketId + "/" + uuidv4() + ".jpg"`
   - Where `ticketId` is generated client-side as a UUID before the ticket insert so the path is known up front. (If the existing `createTicket` flow doesn't accept a pre-generated id, generate the path immediately after insert and update — adapt to the existing pattern.)
   - `await bucket.file(srcParts.join("/")).copy(bucket.file(dstParts.join("/")))` — use the same bucket/path-decomposition pattern at `server/routes.ts:15256-15260`.
   - Collect the new `dstPath` strings into the new ticket's `photos[]` array.
   - On a per-photo copy failure, log loudly but continue with the rest. Aggregate per-ticket photo-copy failures and include in the response.

5. **Create the ticket.** Use `storage.createTicket({...})` with:

   ```ts
   {
     companyId: user.activeCompanyId,
     ticketTypeId: extraBillableTypeId,
     currentStatusId: readyForBillingStatusId,
     title,
     description,
     customerId: item.customerId,
     priority: "normal",
     workType: "extra_work",
     billingBehavior: "invoice_required",
     photos: copiedPhotoStorageKeys, // array
     assignedToId: user.id, // matches snow-events pattern; the generator owns it until billing
     leadTechUserId: leaderUserId,
     crewMemberUserIds: memberUserIds, // includes the leader (existing convention, see routes.ts:6740)
     workCompletedDate: item.completedAt ?? new Date(), // when the field marked it done
     createdById: user.id,
   }
   ```

   Do NOT auto-populate any price/amount field — `estimatedAmount` is included in the description text only. Pricing is admin-keyed downstream by the existing invoicing flow.

6. **Update the campaign item.** Set:

   ```ts
   {
     billingStatus: "ticket_created",
     ticketId: ticket.id,
   }
   ```

   This is the canonical campaign_item → ticket link. Do NOT create a `ticket_links` row — `ticket_links` is for ticket-to-ticket relationships only (see `shared/schema.ts:840`); the campaign_item→ticket relationship lives on `campaign_items.ticketId`.

7. **Append to the response array.**

Response shape:

```ts
{
  generated: number;     // tickets successfully created
  skipped: number;       // eligible items skipped (e.g., already had ticketId)
  failed: number;        // items that errored out partway
  results: Array<{
    itemId: string;
    customerName: string;
    success: boolean;
    ticketId?: string;
    error?: string;
    photoCopyFailures?: number; // count of photos that didn't transfer
  }>;
}
```

Each item is processed independently — a failure on item N does NOT roll back items 1..N-1. Total transaction wrapping is intentionally avoided so that 47 successes aren't lost because of 3 failures.

Logging: on each successful generation, log at info level matching the existing pattern at `routes.ts:6722` and `:7544`: `"Generated Extra Billable ticket {ticketId} for campaign {campaignId} item {itemId} (\"{title}\")"`.

### 2. New: per-item single ticket generation

```
POST /api/campaigns/:campaignId/items/:itemId/generate-ticket
```

Identical behavior to the bulk endpoint but for one item. Same eligibility checks. Returns the same per-item result shape. Used by the per-row "Generate" button on the Billing Queue.

Implementation: factor the per-item generation logic into a helper `generateExtraBillableTicketForItem(item, campaign, user, ticketTypeInfo)` and call it from both endpoints. The bulk endpoint loops over eligible items calling the helper; the single endpoint validates item id then calls the helper once.

### 3. New: campaign billing summary

```
GET /api/campaigns/:campaignId/billing-summary
```

Returns:

```ts
{
  totalCompleted: number;
  totalSkipped: number;
  totalPending: number;
  ticketsCreated: number;
  notYetCreated: number;
  ineligibleItems: Array<{
    itemId: string;
    customerName: string;
    reason: "no_crew_assigned" | "crew_has_no_leader";
  }>;
  estimatedAmountTotal: number | null; // sum of estimatedAmount where set, null if none have it
}
```

The Billing Queue UI uses this for its summary header and the "X items skipped — see why" expandable.

Authorization: admin/office.

## Patterns and conventions

- The bulk-generation endpoint must be **idempotent** — calling it twice in a row should generate zero tickets the second time (since all eligible items will have moved to `billingStatus: "ticket_created"`). Verify in tests.
- Per-item processing must be independent — partial failures don't roll back successful generations.
- Use `data-testid` on every interactive element. Examples: `data-testid="button-generate-all"`, `data-testid="row-billing-${itemId}"`, `data-testid="button-generate-row-${itemId}"`, `data-testid="link-ticket-${ticketId}"`.
- All user-facing strings via i18next. Reuse existing keys where possible — e.g., `campaigns.completed` already exists.
- The bulk endpoint should NOT block the request with a transaction. It loops, processes, and returns. For 100 items this could take 10–30 seconds (mostly photo copies). The client shows an indeterminate progress bar and a "this may take a moment" message after 5 seconds; do NOT add streaming/SSE in this slice — a single POST that returns when done is fine.
- GCS photo copies use server-side `bucket.file(src).copy(bucket.file(dst))` — never download-then-reupload. The blobs stay in the same bucket; the copy is fast and free.
- Match the existing logging patterns at `routes.ts:6722` and `:7544` — `console.log("Generated Extra Billable ticket {id} for campaign {cid} item {iid}")` etc.

## Testing

Add a `vitest` + `supertest` test file at `server/routes/extraBillableCampaign.generateTickets.test.ts` covering:

- Bulk generation succeeds for 3 eligible items, returns counts and per-item results, sets `billingStatus` and `ticketId` on each.
- Idempotency: second call to the bulk endpoint with no body returns `generated: 0, skipped: 3` (the items that already have tickets).
- Items with `assignedCampaignCrewId === null` are filtered out and surface in the summary as `"no_crew_assigned"`.
- Items where the assigned crew has `leaderUserId === null` are filtered out and surface as `"crew_has_no_leader"`.
- Field role gets 403 even if they're a crew leader.
- Cross-company access returns 404.
- Wrong campaign category returns 400.
- Per-item endpoint validates the item belongs to the campaign.
- A simulated GCS copy failure on one photo of one item still allows the rest of the items to generate; the failed-item result has `photoCopyFailures: 1` but `success: true` (the ticket was created with the photos that did transfer).
- The created tickets have correct `ticketTypeId` (Extra Billable), `currentStatusId` (Ready for Billing), `workType: "extra_work"`, `billingBehavior: "invoice_required"`, `leadTechUserId` set to the crew leader, `crewMemberUserIds` containing the leader plus all members.

## Out of scope for this slice (do not build)

- Auto-pricing tickets from `estimatedAmount` (it goes in the description only; pricing is admin-keyed at billing time).
- Editing a generated ticket's photos from the campaign side after generation (use the ticket's own photo flow).
- Un-generating / rolling back a ticket — admins delete the ticket the existing way and reset `campaign_items.billingStatus` manually if needed. v2 work.
- Bulk delete of generated tickets.
- Email notification to the customer when the ticket is created (existing ticket workflows handle this if configured).
- Streaming / progress events from the bulk endpoint (single POST is fine for v1).
- Field crew leader's home dashboard widget (Slice 5).
- Cross-campaign reporting on extra-billable revenue (defer to v2 or use the existing reports infrastructure).
