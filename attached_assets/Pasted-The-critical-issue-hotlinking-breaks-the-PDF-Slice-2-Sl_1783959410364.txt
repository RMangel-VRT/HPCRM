The critical issue: hotlinking breaks the PDF (Slice 2 ↔ Slice 3 conflict)
Slice 2 puts "self-hosting photos" out of scope and says "all images link to thetreefarm.com's CDN." But Slice 3 has to render those photos into the finalized proposal, and I confirmed how that works: proposals finalize server-side via POST /api/proposals/:id/finalize, and PDF generation in this codebase uses pdfkit (doc.image(...)), which needs the actual image bytes at render time — it can't just point at a remote URL. So a hotlinked thetreefarm image means your server has to fetch an external CDN file every time a proposal is finalized. That's fragile: it breaks if thetreefarm reorganizes media (their URLs are Magento cache paths, which do change), rate-limits you, or is down — and it's slow.
You already have the fix in place: the repo has object storage (objectStorage.ts / @google-cloud/storage) that proposal files and photos already use. So the right move is to download each matched photo once during Slice 2 enrichment and store it in your object storage, keeping both the original source URL and the credit. Then Slice 3 just reads a stable local object. It's barely more work in Slice 2 and removes an external dependency from your proposal-generation path.
My recommendation: flip Slice 2's "self-hosting out of scope" line to "download + store in object storage," and add imageStoragePath alongside imageUrl on plant_enrichment. (Browser picker can still use the CDN URL; the PDF uses the stored bytes.)

So you can very likely match deterministically on SKU — strip the size off the availability code, join to thetreefarm's SKU — and fall back to fuzzy only for the stragglers. Much higher accuracy than fuzzy alone. Worth adding to step 3.
