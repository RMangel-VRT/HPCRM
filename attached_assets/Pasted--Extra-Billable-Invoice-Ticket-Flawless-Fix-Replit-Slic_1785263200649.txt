# Extra Billable → Invoice Ticket — "Flawless" Fix (Replit Slice)

Paste this into the Replit AI agent. It finishes Task #589 so the Extra Billable
auto-invoice feature is type-safe and reports the created invoice end to end.

## Context
Commit `00119f2` (Task #589) made `generateExtraBillableTicketForItem` create and
link an Invoice ticket when an Extra Billable (EB) ticket is generated at "Ready
for Billing". The runtime logic is correct and the two new tests pass. Two loose
ends remain:

1. **Type error (breaks `pnpm run typecheck`).** The function now returns
   `invoiceTicketId`, but its return-type annotation was never extended.
   `tsc --noEmit` fails with **TS2353** ("Object literal may only specify known
   properties, and 'invoiceTicketId' does not exist..."). The build (esbuild) and
   vitest transpile without type-checking, which is why it slipped through.
2. **`invoiceTicketId` is not surfaced.** The value is returned by the inner
   function but neither endpoint (bulk generate, single generate) nor the bulk
   `results[]` passes it back to the client, so the UI can't confirm/deep-link the
   invoice that was created.

All edits are in `artifacts/api-server/src/routes/extraBillableBilling.ts` except
the test additions.

## Change 5 — Lock it in with tests

**File:** `artifacts/api-server/src/routes/extraBillableCampaign.generateTickets.test.ts`

Note on test style: this suite drives routes with **supertest directly** —
`await request(app).post("/api/campaigns/camp-1/items/i1/generate-ticket").send({})`
— there is no shared helper. Follow that exact pattern; do not introduce a

In the existing test **"auto-creates an Invoice ticket linked to the Extra

### 5b. Assert the id is absent on graceful degradation — augment, don't duplicate
There is **already** a test in the same `describe` block named
**"still creates the Extra Billable ticket if invoice creation fails"** (~L247)
that sets `ensureInvoiceReturns: null` and asserts `world.ticketLinks.length === 0`.
Do **not** add a second, near-identical test. Instead, extend that existing test
with the response-shape assertions so it fully covers this task:

```ts
  it("still creates the Extra Billable ticket if invoice creation fails", async () => {
    const world = makeWorld({ items: [makeItem()], ensureInvoiceReturns: null });
    const { app } = buildApp(world, "admin");
    const res = await request(app).post("/api/campaigns/camp-1/items/i1/generate-ticket").send({});
    expect(res.status).toBe(200);
    // added for #592: EB ticket still succeeds, but no invoice id is surfaced
    expect(res.body.success).toBe(true);
    expect(res.body.ticketId).toBe("tk-1");
    expect(res.body.invoiceTicketId).toBeUndefined();
    expect(world.tickets.length).toBe(1);
    expect(world.ticketLinks.length).toBe(0);
  });
```

(If you'd rather keep a separately-named test, that's fine too — just give it a
distinct name so it doesn't read as a duplicate of the existing one.)

## Notes / deliberately out of scope
- The PATCH "advance to Ready for Billing" path (routes.ts ~L6805) also copies
  `contractId` and source comments onto the invoice. The generation path omits
  both **on purpose**: a freshly generated EB ticket has no comments yet, and
  campaign-generated EB tickets are not contract-linked. Leave as-is unless you
  later attach EB tickets to contracts.
- No duplicate-invoice risk: EB tickets are created with
  `billingBehavior: "invoice_required"` and are born at Ready for Billing, so if
  one is ever stepped back and re-advanced, the PATCH path's `hasExistingInvoice`
  guard prevents a second invoice.
