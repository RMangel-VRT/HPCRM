# CC1-3: Copy existing contracts into the new tables

## Goal

An admin tool in Settings › Contracts that previews, then copies, every existing contract into the new tables. **Old rows are only read, never changed or deleted.** The old screens keep working on the old tables. Anything the copy can't be sure about is marked `needs_review` with a plain-English `review_note`, so a person can check it later.

Depends on CC1-1 (tables, `contractCatalog.ts`) and CC1-2 (rate card, which must be loaded first).

## Endpoint

`POST /api/admin/contract-center/copy-legacy` in `routes/contractCenter.ts`. Admin only (`adminOnly`).
- Body `{ dryRun?: boolean }`. **Default is a dry run**, the same pattern as `POST /api/admin/migrate-invoices` in `routes.ts`.
- If the company's rate card is empty, return 409 with "Load the standard rates first (Settings › Contracts)".

The response is the same shape for both modes:

```ts
{
  dryRun: boolean,
  summary: { customers: number, agreements: number, terms: number, scopeLines: number,
             billingMonths: number, documents: number, needsReview: number, alreadyCopied: number },
  customers: Array<{
    customerId: string, customerName: string,
    agreements: Array<{
      line: "landscape" | "snow",
      terms: Array<{
        legacyContractIds: string[], seasonLabel: string, startDate: string, endDate: string,
        status: string, billingType: string, annualPriceCents: number | null,
        scope: Array<{ serviceKey: string, quantity: number | null }>,
        flags: string[]            // the review notes; empty = clean
      }>
    }>
  }>
}
```

## What the copy does, per company

Read everything once:
- `contracts`, `contract_services`, `contract_monthly_amounts`, `contract_documents`, `contract_status_history`
- `customer_service_plans`, `customer_rate_sheets`, `customers`, `property_management_companies`
- `term_legacy_sources` (to skip what's already copied)
- `rate_card_items`

Then build the plan in plain functions, so they can be unit tested without a database. Put them in `artifacts/api-server/src/lib/contractCenterCopy.ts`.

1. **Skip contracts already copied.** Any old contract whose id is in `term_legacy_sources` is counted in `alreadyCopied` and ignored. This makes the tool safe to run more than once.
2. **Group by customer, then by line.** Line comes from `LEGACY_CONTRACT_LINE[contracts.service_type]`. A customer with old Maintenance and Snow contracts gets **two** agreements, landscape and snow. Don't merge them into Both; nothing in the old data says they were one document. Add the flag "Has separate landscape and snow agreements; merge into one Both contract if they're signed as one" to both.
3. **Group contracts into terms.** Within an agreement, old contracts with the **same start and end date** become one term. Maintenance, Chemical and Irrigation contracts for the same season usually line up this way. Each distinct date pair is its own term, ordered by start date. `renewed_from_term_id` links each term to the one before it.
4. **Dates.** Old `start_date`/`end_date` are timestamps written from date pickers as UTC instants. Take the calendar date from the **UTC components** (`d.toISOString().slice(0, 10)`). Do not use `companyDateString()` here: a value stored as UTC midnight would become the day before in Denver. If a timestamp's UTC hour isn't 0, 6 or 7, flag "Check start date (stored as <raw value>)". If `end_date` is null, set the end to start + 12 months − 1 day and flag "Had no end date; assumed 12 months".
5. **Season label.** Use `"2026"` when start and end fall in the same year, otherwise `"2025–26"` (en dash, two-digit second year).
6. **Status.** Map from the old contract statuses in the group:
   - Any `active` → `active`.
   - Any `paused` (and none active) → `active`, with the flag "Was paused in the old system".
   - All `ended`, with a later term in the same agreement → `renewed`.
   - All `ended`, with no later term → `lost`, with the flag "Old status was ended; confirm whether it was lost or just expired".
   - More than one term in an agreement mapped to `active` → keep them all, and flag each "More than one active season for this customer and line".
7. **Billing type.**
   - Snow agreements with no monthly amounts: `time_and_materials`. Put the old billing pattern in the term's `notes` ("Old billing pattern: 12-of-12").
   - Snow agreements that do have monthly amounts: `LEGACY_BILLING_TYPE[billing_pattern]`, and flag "Snow contract had monthly amounts; check whether it's a flat seasonal price".
   - Landscape: `LEGACY_BILLING_TYPE[billing_pattern]`. If the contracts in one term disagree, use the first one's pattern and flag "Billing patterns differed: …".
8. **Price and billing months.** `contract_monthly_amounts` store a month number (1–12) and cents, with no year.
   - For each month number, sum the amounts across the term's contracts.
   - Place each month on the first day of the one month inside the term window that has that number. Write one `term_billing_months` row per month with a nonzero amount.
   - If the window is longer than 12 months, or a month number falls outside it, skip that month and flag "Monthly amount for <Mon> doesn't fit the term dates".
   - `annual_price_cents` = the sum of the placed amounts, or `null` when there are none. Landscape terms with no amounts are flagged "No monthly amounts entered".
9. **Mobilization fee.** If any contract in the term `has_mobilization_fee`, add "Mobilization fee $X" to `notes` and flag "Had a mobilization fee; decide where it belongs".
10. **Scope lines** come from `contract_services` of the term's contracts.
    - Map each with `LEGACY_SERVICE_TO_SCOPE[service_type]`. An unknown type maps to `other`, with the flag "Unknown service type <x>".
    - Copy `quantity = annual_count` and `month_spread = monthly_distribution`.
    - Map `service_parameters` into `details` (`stationCount` → `details.stations`; keep `organic` and `visitsPerWeek`). Copy `notes`.
    - `line` comes from the catalog entry and `unit` from the catalog default. `sort_order` is the catalog index.
    - If the same key appears twice in one term, add the quantities and spreads into one line and flag "Combined two <key> lines".
    - A mapping marked `review: true` flags "Mapped <old> to <new>; check it".
11. **Service plans.** Look at `customer_service_plans` for the term's customer, with `year` equal to the term's start year.
    - A plan with `source_contract_ref` pointing at one of the term's contracts is a copy, so don't add a line. If its `expected_quantity` differs from the copied line's quantity, flag "Service plan says N <key>, contract says M".
    - A plan with no `source_contract_ref` whose key isn't already on the term becomes an extra scope line, with the flag "Added from a service plan, not the contract".
    - Plans whose year matches no term are ignored, and counted in the report.
12. **Rates: a full copy per term.**
    - For each active `rate_card_items` row whose line applies (landscape agreements: `landscape`, `irrigation`, `general`; snow agreements: `snow`, `general`), write a `term_rates` row. Copy label, category, unit, minimum and price. Set `card_price_cents`/`card_price_text` to the same card values.
    - Then apply the customer's `customer_rate_sheets` values over `price_cents`:
      - `generalLabor` → `rate_general_labor`
      - `emergencyGeneralLabor` → `rate_emergency_general_labor`
      - `irrigationLabor` → `rate_irrigation_labor`
      - `emergencyIrrigationLabor` → `rate_emergency_irrigation_labor`
      - `handShovelLabor` → `rate_hand_shovel`
      - `plowTruck` → `rate_plow_truck`
      - `skidSteer` → `rate_skid_loader`
      - `atv` → `rate_atv`
      - `iceMeltMaterial` → `rate_ice_melt`
      - `iceMeltApplicationLabor` → `rate_ice_melt_application`
    - `snowBlower`: if it's set and differs from `atv`, flag "Rate sheet has separate ATV and snowblower rates; the new card has one". If `atv` is empty, use `snowBlower` for `rate_atv`.
    - `operatorLabor` has no rate card key: if it's set, flag "Rate sheet has an operator labor rate with no place on the new card".
    - The old rate sheet is per customer, not per season, so the same values go on every term for that customer.
13. **Contact snapshot.**
    - `managing_agent_name` is the linked `property_management_companies.name`, else `customers.management_company`, else null.
    - `property_management_company_id` on the agreement comes from `customers.property_management_company_id`.
    - `project_address` = `street, city, state zip`.
    - `legal_name`, `project_contact`, `contact_phone` and `contact_email` stay null. Phase 5 fills them from the signed contracts. Don't flag these; every term would have them.
14. **Documents.** Each `contract_documents` row becomes a `term_documents` row with `kind = "other"`, the same `version`, `filename`, `storage_object_path`, `mime_type`, `file_size` and `uploaded_by`. `created_at` = the old `uploaded_at`. The file itself isn't copied; both rows point at the same object.
15. **Status history.** Each `contract_status_history` row becomes a `term_status_history` row:
    - `new_status` = the mapped term status for that old value (active → active, paused → active, ended → the term's final status).
    - `note` = "Old system: <old> → <new>".
    - Keep `changed_by` and `created_at`.
16. **Legacy links.** Write one `term_legacy_sources` row per old contract in the term.
17. **Review flag.** `needs_review = true` and `review_note = flags.join("; ")` whenever a term has any flag.

Writes (when `dryRun: false`):
- Use **one transaction per customer**, so one bad customer doesn't block the rest. Record any failure in the report as a flag with the error message.
- Set `created_by` on every term to the admin running the tool.
- The tool never touches `contracts`, `contract_services`, `contract_monthly_amounts`, `contract_documents`, `contract_status_history`, `customer_service_plans` or `customer_rate_sheets`.

## Client: "Copy existing contracts" card

Add a third card to `ContractSettings.tsx`, below the rate card:
- **Header:** title "Copy existing contracts" and one line: "Copies every contract from the old system into the Contract Center. The old screens keep working. Run the preview first; anything uncertain is marked for review, not guessed."
- **Preview** button: a dry run. It shows the summary counts and a table with one row per term: Customer, Line, Season, Dates, Status, Price, Services (count), and Flags. Flags appear as a list under the row; rows with flags are tinted. Add a "Show only rows with flags" toggle.
- **Copy N contracts** button: enabled only after a preview, and confirmed in an inline panel (no `window.confirm`). It runs with `dryRun: false` and then shows the same report with "Copied" in the header.
- If the rate card is empty, disable both buttons and say "Load the standard rates first."

## Tests

Unit tests for `contractCenterCopy.ts` in `artifacts/api-server/src/lib/contractCenterCopy.test.ts`. Use plain objects; no database.
- Three old contracts (Maintenance, Chemical, Irrigation) with the same dates become one landscape agreement with one term, and their services are merged into one scope list.
- Maintenance and Snow contracts for one customer become two agreements, each flagged for a possible merge.
- Two seasons (2024–25 ended, 2025–26 active) become two terms. The first is `renewed` and the second `renewed_from` it.
- A stored start of `2025-11-01T00:00:00Z` gives `2025-11-01`; `2025-11-01T06:00:00Z` also gives `2025-11-01`.
- A null end date gets start + 12 months − 1 day and a flag.
- Monthly amounts {11: 394500, 12: 394500, …12 months} on a Nov 1 – Oct 31 term land on 2025-11-01 … 2026-10-01 and sum to the annual price.
- `irrigation_close` maps to `irrigation_winterization` with a check flag.
- Rate sheet `skidSteer: 22500` overrides `rate_skid_loader` on the term, and `card_price_cents` keeps the card value (24500).
- A contract already in `term_legacy_sources` is skipped and counted.
- A term with no flags has `needs_review = false`.

Also add route tests with `../db` mocked: admin-only access, dry run is the default, and the 409 when the rate card is empty.

## Verify

1. Load the standard rates if you haven't, then run Preview. The counts look right against the old Contracts page (number of active contracts, customers).
2. Spot-check three customers you know (for example Hyland Village HOA) against their old contract cards: dates, monthly amounts, services and documents.
3. Run Copy. Run Preview again: everything shows under "already copied", and nothing would be copied twice.
4. The old Contracts page, the customer Contracts tab, the dashboard and Revenue › Contract audit look exactly as before.
5. Typecheck and tests pass.

## Not in this slice

Any screen that shows the new tables (Phase 2), merging agreements into Both, filling legal names and contacts from signed documents (Phase 5), and changing or deleting anything old.
