# Replit Prompt — Estimate Builder, Slice 1.1: QuickBooks OAuth Connection

## Context

We are beginning the Estimate Builder + QuickBooks integration (master spec: `estimate-builder-design-spec.md`). The end state of the whole project: the CRM owns the product catalog and estimates; QuickBooks receives accurate invoices built from accepted estimates. **This slice builds only the foundation: a per-company QuickBooks Online OAuth2 connection**, managed from Settings, with encrypted token storage, automatic refresh, and a health status. No customer sync, no invoices, no estimates in this slice (those are Slices 1.2+).

Deployable end state: an admin opens Settings, clicks "Connect to QuickBooks," completes Intuit's consent flow, and returns to Settings showing a healthy connection (company name, environment, status). Tokens refresh automatically. Disconnect works. The existing `qbo_write` feature-flag toggle gains real server-side meaning: a helper that later slices will use to gate all QBO write operations.

This slice should land in a deployable, production-quality state. Do not stub anything you say you've built.

## Server

### 1. Token encryption — `artifacts/api-server/src/services/qboCrypto.ts`

AES-256-GCM via Node `crypto`, key from `QBO_TOKEN_ENC_KEY`. Store as `iv:ciphertext:authTag` (hex or base64). Export `encryptToken(plain): string` / `decryptToken(enc): string`. Unit-test round-trip + tamper detection (bad auth tag throws).

### 2. QBO client service — `artifacts/api-server/src/services/qboClient.ts`

The single choke point for all QBO API access, used by every later slice.

- `getAuthorizeUrl(state)` → `https://appcenter.intuit.com/connect/oauth2` with `client_id`, `scope=com.intuit.quickbooks.accounting`, `redirect_uri`, `response_type=code`, `state`.
- `exchangeCodeForTokens(code, realmId)` / `refreshTokens(connection)` → POST `https://oauth.platform.intuit.com/oauth2/v1/tokens/bearer` (Basic auth from client id/secret). Persist encrypted tokens + expiries (access ~1h, refresh ~100 days — read from the response fields, don't hard-code).
- `revoke(connection)` → POST to Intuit's revoke endpoint; then delete the row.
- `qboRequest(companyId, method, path, body?)` → resolves the company's connection, **auto-refreshes if the access token expires within 5 minutes** (single-flight: concurrent callers must not double-refresh — per-company in-flight promise with a 30s timeout + AbortController so a hung refresh can't wedge the lock), calls `https://{sandbox-}quickbooks.api.intuit.com/v3/company/{realmId}{path}` with `minorversion` pinned. On 401: one refresh + retry, then mark the connection failed and throw a typed error. Base URL from the connection's `environment`.
- **Refresh-failure classification** (production-proven pattern; implement exactly): parse Intuit's error body — `invalid_grant`/`invalid_refresh_token` → `expired` (stale refresh token); `access_denied`/`authorization_revoked`/`revoked_token` → `revoked`; HTTP 5xx / `server_error` / `temporarily_unavailable` → transient (do NOT change connection status; retry later); other 4xx → `error` (reconnect required). Non-transient categories set `status` + a human-readable `lastErrorMessage` ("Refresh token expired. Please reauthorize QuickBooks."). Transient failures never flip a healthy connection to a broken status.
- **Background proactive refresh:** a simple interval job (piggyback on an existing scheduler if one exists; otherwise `setInterval` at boot, ~30 min) that runs the proactive refresh for every connected company — so tokens stay fresh even when nobody is using QBO features. Skips connections already in a failed status.
- `getCompanyInfo(companyId)` → GET `/companyinfo/{realmId}`; used post-connect (store `qboCompanyName`) and by the health check.
- `isQboWriteEnabled(companyId)` → reads `settings.featureFlags` JSON, returns `!!flags.qbo_write`. Exported for later slices; nothing calls it yet except a unit test.

### 3. Routes — `artifacts/api-server/src/routes/qbo.ts`

- `GET /api/qbo/connection` (admin, office): status view — `{ status, environment, qboCompanyName, realmId, connectedAt, accessTokenExpiresAt, lastErrorMessage }` or `{ status: "not_connected" }`. Never returns tokens.
- `POST /api/qbo/connect` (admin): generates a random `state`, stores it server-side bound to the session/user + companyId (10-min expiry), returns `{ authorizeUrl }`. Frontend redirects the browser to it.
- `GET /api/qbo/callback`: validates `state` (reject on mismatch/expiry), exchanges `code` + `realmId`, upserts the company's `qbo_connections` row, fetches CompanyInfo for the display name, then redirects to Settings with `?qbo=connected` (or `?qbo=error&reason=…`).
- `POST /api/qbo/disconnect` (admin): revoke + delete row.
- `POST /api/qbo/test` (admin, office): calls `getCompanyInfo`, returns ok/fail — the "Test connection" button.
