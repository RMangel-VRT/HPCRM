# C3: Billing hand-off (work leaves Tickets, Mike gets "To invoice")

> Assumes 00-RULES-C.md, C1, C2, F1 and F2 are merged. **Line numbers are from GitHub `c4f4bd1`**; find code by its content. **No schema change, no migration.** The mockup Randy approved is "High Plains Billing Flow"; this slice builds it.
>
> The risks here: hiding something billable so that nobody sees it, and the To invoice list disagreeing with the Billing page. Both lists come from **one** server query (§1). Anything at Ready for billing that has no invoice must still show somewhere (§1, "stranded").

## The rule (Randy's words, made precise)

**Ownership follows status.** While the crew is working a job, it lives on **Tickets**. When it reaches **Ready for billing**, the job and its Invoice ticket leave Tickets and appear as **one row** in the billing list. That list has two views of the same data:

- **My Tickets → To invoice** for the billing person (Mike). This is where he works. He does not need a second place to check.
- **Billing** in the sidebar for admin and office. This is oversight: every charge, with an Assignee column.

"Billing items" means:
- every Invoice ticket (`typeKey === "invoice"`), open or closed;
- every non-Invoice ticket whose status is `ready_for_billing`.

## 1. Server: one billing list

### 1a. Who counts as billing

`company_users.tags` already holds `"billing"`; the auto-created invoice is assigned to that user (`rfbInvoiceAutoCreate.ts` ~L153, routes.ts ~L7033, ~L7275, ~L8006).

- Add `activeTags: string[]` to `UserWithContext` (`auth.ts` ~L11), filled from the active membership in **both** places `activeRole` is set (~L50 login and ~L137 deserialize). Default to `[]`.
- Confirm `/api/auth/me` returns it, and add it to the client's `UserWithCompanyContext` (`hooks/use-auth.tsx`).
- New helper in `lib/billing.ts` (server, new or existing file of your choice): `canSeeBilling(user) = activeRole is admin or office, OR activeTags includes "billing"`.
- Client `lib/billing.ts`: change `canViewBilling(role)` to `canViewBilling(user)` with the same rule, and add `isBillingPerson(user) = activeTags includes "billing"`. Update every caller.

### 1b. `GET /api/pending-invoices` (routes/pendingInvoices.ts)

- **Guard:** `canSeeBilling(user)`, otherwise 403 as today.
- **Response stays an array.** Add `kind: "invoice" | "stranded"` to every row. Existing rows are `"invoice"`.
- **New query params:**
  - `scope=mine`: invoice rows where `assignedToId = user.id` **or** `assignedToId IS NULL`, plus every stranded row. `scope=all` (the default) returns everything, as today.
  - `view=recent`: instead of pending invoices, return Invoice tickets in a **final** status whose `completedAt` falls in the last 30 Colorado days (`companyToday`, `addCalendarDays`, `companyDayBounds` from F2), newest first. Same row shape, plus `invoiceNumber` and `completedAt`. `scope` applies too. No stranded rows in this view.
- **Stranded rows** (only in the default pending view): a non-Invoice ticket in this company at status `ready_for_billing` whose `billingBehavior === "invoice_required"` (or whose type passes `isInvoiceEligibleType`), with **no** `invoice_for` link where it is the source.
  - Find them with one query for the RFB status ids and one bulk `ticket_links` lookup. **No per-row queries.**
  - Row shape: the job's own `id`, `title`, `customer`, `workCompletedDate`, `ageDays`; `sourceTicket` = the job itself (with `typeKey` / `typeName`); `kind: "stranded"`; `invoiceCategory: null`; `assignedToId` = the job's assignee.
- Keep the C2 cap-free query and the scoped-link rule.

### 1c. "Create invoice" for a stranded job

`POST /api/tickets/:id/create-invoice` (routes.ts ~L7243) currently allows only Estimate Request and Project. **Also allow** any non-Invoice ticket that is at `ready_for_billing` with `billingBehavior === "invoice_required"`. Everything else in the route stays as it is: the 409 if an invoice already exists, the billing-user assignment, the link and the comment copy. Guard it with `canSeeBilling`, in addition to whatever it checks today.

**Tests (vitest):**
- `scope=mine` returns the user's invoices plus unassigned ones, never another user's.
- A billable Task at RFB with no invoice comes back once, as `kind: "stranded"`. After `create-invoice` it comes back once, as `kind: "invoice"`.
- A contract Task never appears. (It can't reach RFB, so this test covers the eligibility check.)
- `view=recent` returns an invoice marked invoiced today and excludes one completed 31 days ago. Run it under `TZ=UTC` at 8 pm Colorado time.
- A user tagged `billing` with role `field_manager` gets 200; an untagged `field_manager` gets 403.
- Query count does not grow with the number of rows.

## 2. Client: Tickets is the work

In `pages/TicketsList.tsx`:

- Add one shared helper, `isBillingItem(ticket, typeById, statusById)`, in `lib/billing.ts`, using `typeKey` / `statusKey` only. Every list below uses it.
- **Default:** hide billing items from the **List**, **By Type** and **By User** views, from both the Open and Completed sections. The By Type board loses its Invoice column.
- **"Show billing items" toggle** next to the view buttons. When it's on, billing items appear in a muted **"With billing"** section below Open (List) or in their normal columns (boards). It's off on every page load; don't persist it.
- **Remove the Billing view-mode button** (~L649) and the `"billing"` view mode. Anyone who arrives with `?view=billing` is redirected to `/dashboard/billing`. Update `lib/ticketListReturn.ts` (~L43) to match.
- Counters such as "Needs scheduling" are unaffected. Confirm it.
- **Leave the customer page's `TicketListView` alone.** A property's history should still show everything.

## 3. Client: My Tickets gets "To invoice"

In `pages/MyTickets.tsx`, in the **non-`showTabs` path only** (landscape supervisors keep My Work unchanged):

- **Tabs:** **To invoice (n)** and **Other tickets (n)**. Show them only when `isBillingPerson(user)` is true **or** the `scope=mine` list is non-empty. Otherwise the page looks exactly as it does today.
- **Default tab:** To invoice for billing people; Other tickets for everyone else. Read and write `?tab=invoice|other` so links and Back work.
- **Other tickets** is today's content (open and completed sections, filters, board) **minus billing items**, using the same `isBillingItem` helper.
- **For users without the tabs,** billing items are still removed from their open list. The Ops Manager's job at Ready for billing is now Mike's. Show one muted line under Open when any were removed: "2 of your jobs are with billing", which links to nothing.

**To invoice tab:** reuse `BillingView`, refactored to take `scope: "mine" | "all"` and a `showAssignee` flag.
- **Header:** `N charges waiting`, a **Waiting / Recently invoiced** switch (`view=recent`), and **Group by property** (the existing per-viewer preference).
- **Columns:** Property · Charge · From · Work completed · Category · Age · action. **Age** is red at 5 days or more.
- **Invoice rows:** clicking the row opens the Invoice ticket, as today. A **Mark invoiced** button on the row opens a small dialog with an optional **QuickBooks invoice #**. On confirm it sends `PATCH /api/tickets/:invoiceId` with `{ currentStatusId: <invoiced status id>, invoiceNumber }`.
  - Confirm the PATCH accepts `invoiceNumber` through `pickProvided`, and that C2's parent-advance runs, so the Task goes to Done.
  - Use the same confirmation wording as the Dashboard queue: it changes status only, no QuickBooks sync.
  - On success the row leaves the list and a toast says "Invoiced. <job title> is Done." Use "…closed." when the parent didn't advance because sibling invoices are still open.
- **Stranded rows:** a warm background, the subtitle "Ready for billing, no invoice yet", and a **Create invoice** button calling §1c. Afterwards the row becomes a normal invoice row.
- **Recently invoiced:** read-only rows with the invoice # and invoiced date. No buttons.
- **Footer note:** "Same list as the Billing page, filtered to you, plus any job stuck at Ready for billing."
- **Invalidate** `/api/pending-invoices` (prefix), `/api/tickets/my`, `/api/tickets` and `/api/dashboard/action-queue` after Mark invoiced and Create invoice.

## 4. Client: Billing page (oversight)

- **New route** `/dashboard/billing`, a page rendering `BillingView` with `scope="all"` and `showAssignee`. It gets the same Waiting / Recently invoiced switch, group toggle, row actions and stranded rows as §3. Protect it with `canViewBilling(user)`.
- **Sidebar** (`components/AppSidebar.tsx`, `getDashboardItems` ~L139): add **Billing** under My Tickets for users who pass `canViewBilling`, with a count badge (pending plus stranded, from the same query key). **Don't** show it to a billing person whose role isn't admin or office; they use To invoice.
- Add a `nav.billing` i18n key in en and es.

## 5. Landing and the Dashboard

- **Login** (`LoginPage.tsx` ~L20, ~L37) and `getDefaultRedirect` (`App.tsx` ~L207): a billing person lands on `/dashboard/tickets/my?tab=invoice`. Everyone else is unchanged.
- **Dashboard "Needs you" queue:** leave the items and their Mark invoiced action alone. On the **Billing** filter chip's panel, add a link: "Open To invoice →" (`/dashboard/tickets/my?tab=invoice`) for billing people, and "Open Billing →" (`/dashboard/billing`) for other admin/office users.

## 6. Read-only checks in production (report the counts)

1. **Stranded jobs:** the §1b stranded definition, counted. Randy will clear them from the new screen.
2. **Pending invoices by assignee,** including unassigned, so we know what Mike's tab will show on day one.
3. **Billing-tagged users:** how many active `company_users` have the `billing` tag, and their roles. If it isn't exactly one, say so in the **first line** of the report.

## Done when

- **Checked end to end once in dev:**
  1. A billable Task goes to Ready for billing.
  2. It disappears from Tickets (List and both boards) and from the assignee's My Tickets.
  3. It appears once in the billing person's To invoice tab and on the Billing page.
  4. Mark invoiced with an invoice number: the row moves to Recently invoiced and the Task is Done.
  5. "Show billing items" on Tickets brings the job and its invoice back in the muted section.
- A stranded job appears with Create invoice and becomes a normal row afterwards.
- The To invoice tab count, the Billing sidebar badge and the Dashboard Billing filter agree for an admin who is also tagged billing.
- `?view=billing` redirects; landscape supervisors' My Work is unchanged; the customer page is unchanged.
- No DOM-nesting warnings: row buttons sit outside any link.
- New tests pass, the typecheck shows no new diagnostics, and the §6 counts are in the report.
