# Slice V1 (FINAL) — Ticket detail: type identity, work thread, stepper

**This supersedes `slice-V1-detail-view.md` and corrections 1, 2 and 3. Replace the #617 body with this and discard the rest.**

One file: `artifacts/highplains-crm/src/pages/TicketDetail.tsx`. Builds on V0 (`e41c9a8`), which landed the CSS tokens, `ticketVisuals.ts`, and the narrowed response shapes. Line numbers are against commit `e41c9a8`.

Design source is `ticket-visual-system-mockup.html`. **The agent cannot open it** — all values are inlined here. The palette was validated with a colorblindness/contrast checker across all pairs in both modes; do not substitute "nicer" colors.

---

## Three visible changes

1. Header wears the ticket type's hue — tint wash plus a proper type chip and a universal status pill.
2. A **work-thread bar** above the tabs, always visible and navigable **both ways**, replacing the status-gated one-directional invoice card.
3. The workflow tab becomes a **stepper**, replacing one full Card per status (RFP Request currently renders seventeen).

## Step 8 — Work-thread bar

Insert after the header container from Step 6, before the sticky tab row at ~L1037.

```tsx
{(() => {
  const child  = linkedTickets.find(lt => lt.link.linkType === "invoice_for" && lt.relationship === "source" && lt.ticket);
  const parent = linkedTickets.find(lt => lt.link.linkType === "invoice_for" && lt.relationship === "target" && lt.ticket);
  if (!child && !parent) return null;

  // Always render in real order: originating work → invoice.
  const nodes = parent
    ? [{ ...parent, isCurrent: false, stage: "Originating work" },
       { ticket, ticketType, currentStatus, isCurrent: true, stage: "Billing stage" }]
    : [{ ticket, ticketType, currentStatus, isCurrent: true, stage: "Originating work" },
       { ...child!, isCurrent: false, stage: "Billing stage" }];

  return (
    <div
      className="flex flex-col rounded-t-xl border border-b-0"
      style={{ borderColor: `color-mix(in srgb, ${hue} 30%, var(--border))` }}
      data-testid="bar-work-thread"
    >
      <div className="flex items-stretch overflow-x-auto p-1.5">
        {/* "WORK THREAD" label, then nodes separated by ChevronRight */}
      </div>
      {isAwaitingInvoiceCompletion && (
        <p className="px-3 pb-2 text-[11.5px] text-muted-foreground" data-testid="text-awaiting-invoice">
          Complete the linked invoice to advance this ticket to its final status.
        </p>
      )}
    </div>
  );
})()}
```

Each node: type icon, bold type name, and muted `{stage} · {status name}` beneath. The non-current node is a `Link` to `/dashboard/tickets/${n.ticket.id}`; the current node is not a link and gets:

```
background: color-mix(in srgb, ${hue} var(--tt-tint), var(--background));
borderColor: color-mix(in srgb, ${hue} 55%, transparent);
```

Separator is `ChevronRight` in `color-mix(in srgb, ${hue} 50%, var(--muted-foreground))`. **Both nodes wear the same hue** — the parent's. That is the feature.

**Why the note matters:** `isAwaitingInvoiceCompletion` (~L741) **hides the advance button** when a ticket sits at Ready for Billing with an incomplete invoice. The card deleted in Step 7 was the only thing explaining that. Without this line the user sees no advance button, no error, and nothing to read. **Do not modify `isAwaitingInvoiceCompletion` itself** — it matches on a status *name*, which this slice leaves alone.

If joining the bar to the tab row visually conflicts with the tab row's `sticky top-0`, keep sticky and drop the visual join.

## Step 9 — Workflow tab becomes a stepper (region ~L2177–2280)

**Keep verbatim:** the RFP branch-filter IIFE producing `filteredStatuses` (it matches status *names* — later slice), and the `visitedIds` / `isCurrent` / `isCompleted` derivation.

After `filteredStatuses` is computed:

```ts
const selectedStatus = filteredStatuses.find(s => s.id === selectedStatusId) ?? currentStatus;
const progressIndex  = filteredStatuses.findIndex(s => s.id === ticket.currentStatusId);
```

The `?? currentStatus` fallback handles first render, the ticket advancing while a step is selected, and the RFP branch filter removing the selected step. `progressIndex` tracks the **current** status so the counter does not move as you click through steps.

Label above the rail: `PROGRESS · {progressIndex + 1} OF {filteredStatuses.length}`, uppercase muted 11px.

**≤ 8 steps — continuous rail.** Equal-width segments, a 5px rounded bar above a two-line clamped label:

* completed → `color-mix(in srgb, ${hue} 78%, var(--border))`
* current → `STATUS_STATE_VAR[deriveStatusState(status)]` with `box-shadow: 0 0 0 3px color-mix(in srgb, <same> 26%, transparent)`
* upcoming → `var(--border)`
* `actionType === "waiting"` → overlay `repeating-linear-gradient(135deg, transparent 0 3px, rgba(255,255,255,.55) 3px 6px)` on the bar

**> 8 steps — collapsed dot rail** (unless `stepperExpanded`). Show first, current−1, current, current+1, last; insert a `+N more` pill (dashed border, muted) for each skipped run, calling `setStepperExpanded(true)`. Dots 9px, 11px for current, same colour rules; connectors 1.5px lines, `color-mix(in srgb, ${hue} 70%, var(--border))` once passed. Expanding must not change the selected step.

**Below the rail, one detail panel** for `selectedStatus`: its `description` and its captured field values, using the existing `statusFields` / `getFieldValue` logic moved verbatim (`getFieldValue` is defined at ~L940, above this block). **Preserve the existing `(isCompleted || isCurrent)` gate** — a step the ticket has never reached shows no values. This panel is why the stepper is not a pure replacement: the old Cards displayed these values and they must not be lost.

Clicking a step selects it. Optionally carry `data-testid={`card-status-${status.id}`}` onto each step node to preserve the old selectors.
