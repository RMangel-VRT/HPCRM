# High Plains CRM — Mobile App v1 Design & Implementation Slices

> **For the next Claude:** This file is self-contained. It captures the full context, design decisions, screen specs, and implementation slices for the v1 field-facing mobile app.
>
> **Two projects are in play:**
>
> 1. **Web app (the existing High Plains CRM)** — React 18 + TypeScript + Vite + Tailwind + shadcn/ui (Radix) + Wouter + TanStack Query v5 + React Hook Form + Zod + Drizzle ORM + Postgres + i18next (en + es). Multi-tenant with `companyId` on every table. Used by admin/office; not touched by crews. **Backend work in each slice (schema, API endpoints, admin UI extensions) lands here.**
> 2. **Mobile app (`highplains-mobile`, existing Expo project)** — React Native via Expo. **Mobile UI work in each slice lands here.** Each slice should begin by inspecting this project's existing conventions (Expo SDK version, routing — Expo Router vs React Navigation, styling — NativeWind vs StyleSheet, state management, auth/session storage) and matching them. Do NOT introduce new conventions if the project already has one.
>
> Each slice clearly labels which parts are **Web** vs **Mobile** work.

---

## 1. Vision

The High Plains CRM mobile app is the **field crew supervisor's daily command center**. It tells the supervisor what their crew is doing today, where, and what specifically needs to happen at each property — and it captures photos, notes, and flagged issues back to the office without a phone call. It is field-facing only. All admin, office, scheduling, billing, and property-data entry stays on the existing web app.

The guiding sequence for v1 is: **Today → Property → Ticket → Site Notes → Checklist Items → Photos/Notes → Complete**.

## 2. Admin goals (full brief from Randy)

Reproduced verbatim so design decisions can be traced back.

**Main Goal.** Turn the High Plains CRM into a field-ready mobile tool that helps crews clearly understand: what they need to do, where, when it needs to be done, and what information they need to do it correctly. Reduce confusion, limit back-and-forth communication, and make the data already in the CRM actually useful in the field.

**1. Make Daily Responsibilities Clear.** Crews should be able to quickly see which properties they're responsible for, what services need completing, priority, special instructions, work type (contract / extra / estimate / irrigation / admin), and what's already done vs pending. Avoid the crew having to guess, call the office, or rely on memory.

**2. Create a Simple "Today's Work" Experience.** The app should open to a clear daily work screen showing today's assigned properties, service types, start/finish status, notes/warnings, attached photos/docs, and anything overdue.

**3. Give Crews Access to Property-Specific Information.** Each property profile should include: name, address, manager/contact, contracted services, site notes, gate codes, pet station locations, irrigation controller locations, known problem areas, past work history, photos, maps. Crews shouldn't walk into a property blind.

**4. Connect Tasks to the Right Property Data.** When a crew opens a task, show only the information that matters to that specific task. Mowing shows mowing context. Irrigation shows controller/zone context. Pet station shows station counts and locations. Landscape project shows scope and materials.

**5. Make Job Instructions Easy to Understand.** Translate admin-level CRM data into field-level instructions in plain language ("Trim shrubs along north fence line," "Check Controller A, Zones 1–12," "Install 6 tons of river rock around Building H," "Empty all pet stations and restock bags," "Take completion photos before marking finished").

**6. Support Photos and Field Documentation.** Crews can upload before/progress/completion photos, add notes, mark materials used, record issues, flag work that couldn't be completed, attach photos to a task, property, or service visit.

**7. Create Accountability Without Making the App Hard to Use.** Track task status, start/complete time, crew assigned, photos submitted, notes added, missed/skipped items, follow-up needed — without micromanaging.

**8. Reduce Office-to-Field Communication Problems.** The app should answer common crew questions: where is this property, what are we doing here, what's included in the contract, where is the controller, what did we do last time, special notes, photos required, who's responsible, is this billable extra vs contract.

**9. Make Data Useful Instead of Just Stored.** Put the right information in front of the right person at the right moment.

**10. Support Different Crew Types.** Maintenance, irrigation techs, snow crews, landscape project crews, supervisors, managers — each needs a different view. **v1 is maintenance-only.**

**11. Make Completing Work Simple.** Open task → review instructions → complete → add notes/photos if required → mark complete → flag follow-up if needed. No digging through multiple screens.

**12. Help Build Long-Term Property History.** Every completed task adds to the property record: what, when, who, issues found, photos, follow-up, repairs.

**Vision statement.** The mobile app should be the field crew's daily command center. It should clearly show what needs to be done, provide the property information needed to do it correctly, and make documentation simple enough that crews will actually use it.

**Development direction.** Build the mobile app around the crew's daily work first, then layer in property data, documentation, maps, and history in a way that supports that daily workflow. Don't start with every feature the CRM has.

## 3. Decisions made in design conversation

These are locked for v1 unless explicitly revisited.

**Atomic unit of work** — One **ticket per property visit**, containing a flat checklist of **work items**. A mowing visit might have items like "Mow common areas," "Trim along walkways," "Empty pet stations (4)," "Blow off hardscape." Status lives at both ticket level (not started / in progress / complete) and item level (open / done / skipped).

**v1 role** — Maintenance crews only. Irrigation, snow, landscape project, and supervisor-roll-up views are explicitly v1.1+.

**"Found something" workflow** — Photo + tag + short note → routed directly to the admin's inbox. The admin triages from there (reply, create new ticket, message customer, etc.). Tags drive sorting and eventual auto-routing.

**Devices** — One device per **crew supervisor (foreman)**. Other crew members do not use the app. The supervisor is the authenticated user; tickets, completions, and flags are attributed to the supervisor's crew.

**Clock-in** — Lightweight only. Day starts when the supervisor opens their first ticket; per-ticket arrival/completion timestamps are captured automatically. No per-employee or per-item time tracking in v1.

**Connectivity** — Online-mostly. Today's tickets and site notes are cached on app launch so dead-zone reads work. Photos and notes are queued and synced when service returns. Full offline-first (creating brand-new flags with no network) is v1.1.

**Tech approach** — Build the mobile app inside the existing **Expo `highplains-mobile` project**. Do not start a new project. Do not build a PWA. The existing CRM's web app is untouched on the mobile side — but each slice extends the web app's API surface and (where noted) extends its admin UI to support the new fields the mobile app needs. Server-side work (schema, endpoints) ships through the same Replit-prompted slice format already used for web slices in this repo. Mobile-side work ships against the Expo project's own development and release workflow (EAS Build / TestFlight / internal Android testing — confirm what's already configured).

**Auth approach (assumed, confirm in Slice 0)** — The Expo app authenticates against the existing web API using a token-based flow (likely already in place). All `/api/m/*` mobile endpoints accept the same authenticated user context (`UserWithContext` with `companyId`) the web app uses. If a token flow doesn't yet exist, Slice 0 adds one.

## 4. Information architecture

Three primary surfaces in a bottom tab nav, plus a persistent Flag entry from the header.

**Today (home tab)** — Opens here by default. Vertical list of today's tickets in route order. Each ticket card shows: property name, address, scheduled time, service summary, status pill. Currently-active ticket is visually emphasized. Day summary line at top ("2 of 5 stops complete · Started 7:12 AM"). A "+ Flag" button lives in the top-right of the header. A "Week" toggle can switch to a 7-day view (v1.1 if cut for scope).

**Properties (directory tab)** — Searchable list of all company properties. Used for non-today lookups. Tapping a property opens the **full property profile**, which is the union view of all property data. The ticket detail screen pulls a **filtered subset** of this profile relevant to the active service type.

**Me (profile tab)** — Supervisor profile, my week schedule (richer than Today's single-day view), recent completions, sign out, settings (notification preferences).

**Flag entry points (cross-cutting)** — Top-right "+ Flag" button on every screen. Also a "Flag issue" button at the bottom of every ticket detail. The flag composer is the same screen regardless of entry point; entry point pre-fills context (property, ticket).

What does **not** get its own tab:
- Property Maps — lives inside the property profile and inside ticket detail when relevant
- Ticket list — already represented by Today; "all my open tickets including future" is a filter on Today or a view inside Me
- Schedule — collapsed into Today (single day) + Me (week)

## 5. Screen-by-screen specs

### 5.1 Today (home)

**Purpose** — Answer "what is my crew doing right now and what's next" within 1 second of opening the app.

**Layout (top to bottom):**

1. Header
   - Left: "Today" + secondary line with date ("Friday · May 8")
   - Right: "+ Flag" button (compact, amber/warning color)
2. Day summary strip
   - "2 of 5 stops complete · Started 7:12 AM" (or "Day not started" before the first ticket is opened)
3. Vertical scrolling list of stop cards in route order
4. Bottom tab nav: Today (active) · Properties · Me

**Stop card content:**
- Tiny label "STOP {N}" (in route order, not ticket ID)
- Property name (primary, ~16px, weight 600)
- Address + scheduled time on one line, secondary color
- Service summary in plain language ("Mow · Trim · Pet stations · Hedge trim")
- Status pill: **Not started** (neutral) / **In progress · X of Y** (info color) / **Complete** (success) / **Flagged** (warning)
- Currently-active stop gets a 1px info-color border to stand out

**Card tap target** — Entire card is tappable, opens the ticket detail. Minimum touch height: 88pt (card padding + content).

**Swipe actions on cards** (right-swipe → quick action menu using a Reanimated swipeable row):
- Navigate (deep-links to Apple Maps / Google Maps with address)
- Mark complete (with confirmation if items remain unchecked)
- Skip stop (requires reason from a short list)

**Empty state** — "No stops scheduled for today. Pull down to refresh." with a refresh icon. Day summary strip hidden.

**Loading state** — 3 skeleton cards.

**Error state** — Alert banner at top: "Couldn't load today's stops — using last cached data" with retry button. The cached list still renders below.

### 5.2 Ticket detail

**Purpose** — Give the supervisor everything needed to do this visit correctly, capture work as it happens, and complete it.

**Layout (top to bottom):**

1. Header
   - Left: back arrow
   - Center: property name (primary), address (secondary)
   - Right: "Navigate" button (deep-links to maps)
2. Meta line
   - "Maintenance · 9:30 AM · In progress"
3. **Site Notes** card — curated for this service type (see "Curated property info" below)
4. **Work Items** section
   - Header: "Work items · X of Y"
   - Flat list of checkable rows
   - Each row: checkbox, item title, optional inline instruction line ("36" decks only — no zero-turns on slopes"), optional "photo required" badge
5. **Photos** section
   - Header: "Photos · N added"
   - Horizontal row of thumbnails + "+" tile to add more
6. **Notes** section (collapsed by default to "+ Add note" button)
7. Pinned bottom action bar (respects safe-area insets)
   - Left: "+ Flag issue" (secondary)
   - Right: "Mark complete" (primary)

**Curated property info ("Site Notes" card)** — Pulled from the property profile but filtered to fields relevant to today's service type. For maintenance v1, show:
- Gate code (if any)
- Pet station count + locations (if pet station service is on the ticket)
- "Watch out" notes (free text, admin-curated, tagged with a `relevantTo` value for service types)
- Last visit summary (date + crew)
- Any irrigation problem area markers if marked "affects mowing"

What's **not** in the Site Notes card by default but available via "View full property" link at the bottom: contract details, full history, all photos, all property managers, full map.

**Work item rules:**
- Items have three states: open, done, skipped (with reason)
- Tapping the checkbox toggles open ↔ done
- Long-press (or swipe) reveals "Skip" option which opens a sheet: out of supplies / inaccessible / weather / customer request / other (free text)
- Items marked "photo required" cannot transition to done without at least one ticket-attached photo captured after `startedAt`
- Items are ordered by `displayOrder`, with sub-orderings by service type

**Mark complete behavior:**
- All required items done (or skipped) and required photos attached → ticket completes, `completedAt` set, supervisor returns to Today
- Anything required missing → soft confirmation modal lists what's missing and offers "Complete anyway" (with reason note required) or "Cancel"
- Skipped items appear in the ticket history and the admin's daily summary

### 5.3 Property profile (full)

**Purpose** — Browse-able directory entry for the property when crews need info outside of today's assigned work.

**Layout:**

1. Header: property name, address, "Navigate" button, "+ Flag" button
2. Sticky tab bar: **Overview · Site Notes · Services · Map · History · Photos**
3. Overview tab:
   - Contact: property manager name + phone (one-tap call via `Linking`) + email (one-tap email)
   - Service types currently contracted, with frequency
   - Special access info (gate code, "knock first," etc.)
4. Site Notes tab:
   - All notes grouped by relevance tag (mowing / irrigation / pet stations / chemical / general)
   - Each note has author + date
5. Services tab:
   - Read-only list of contracted services + included scopes
   - "What's NOT included" section if admin has populated exclusions
6. Map tab:
   - Embedded property map. The existing web property-maps tool likely exports a static image (PNG/SVG/PDF); render that for v1. Tap → opens full editor in the web app via a `Linking.openURL` deep link
7. History tab:
   - Reverse-chronological list of completed visits
   - Tap a visit → completion summary, photos, items completed/skipped
8. Photos tab:
   - Grid of all property-attached photos (not ticket-attached)
   - Tap to view full screen via a lightbox component (use whatever is already in `highplains-mobile`; if nothing, `react-native-image-zoom-viewer` or similar — inspect first)

### 5.4 Flag composer

**Purpose** — Capture a field-discovered issue in under 30 seconds and route it to the admin.

**Entry points** — Top-right "+ Flag" on any screen; "+ Flag issue" at bottom of ticket detail; "+ Flag" on property profile header.

**Layout (full-screen modal):**

1. Header: "Cancel" (left) · "New flag" (title) · "Send" (right, disabled until required fields filled)
2. **Photo** (required) — Big tile that opens the camera via `expo-camera` or `expo-image-picker` (inspect existing usage). After capture, shows thumbnail + "Retake" + "Add another".
3. **Tag / Category** (required) — Single-select chip group, 2-column grid:
   - Irrigation issue
   - Property damage
   - Access problem
   - Customer interaction
   - Material / supply needed
   - Safety concern
   - Question for office
   - Other
4. **Property** (auto-filled when launched from ticket/property; manually pickable from a search field when launched from Today's header)
5. **Linked ticket** (auto-filled when launched from a ticket; omitted otherwise)
6. **Short note** (optional textarea, 280 char)
7. Submit → flag is created server-side, push notification fires to admin, modal closes, supervisor returns to where they were. Toast: "Flag sent."

**Offline behavior** — Flag is staged in local persistence (AsyncStorage + `expo-file-system` for the photo) if no network; sync attempt on next connection. UI shows the flag locally with a "Pending" badge until confirmed.

### 5.5 Me (profile)

**Purpose** — Supervisor's account info, week schedule, recent work, and settings.

**Layout:**

1. Header: name, role ("Crew Supervisor"), crew name
2. Week schedule card — 7-day strip showing daily ticket counts and any flagged items
3. Recent completions list — last 10 completed tickets with timestamps
4. Settings:
   - Notification preferences (push on/off, types)
   - App version / build number (from `expo-constants`)
   - Sign out

## 6. Cross-cutting design rules

**Typography & sizing** — Minimum body font 14pt; minimum tap target 44×44pt (iOS HIG) / 48dp (Material). Headings: ticket name 16pt / weight 600; section labels 11pt uppercase tracked. Never lighter than 400 weight on white. Use the system font stack (San Francisco on iOS, Roboto on Android) unless `highplains-mobile` already loads a brand font.

**Color** — Use the color tokens already defined in `highplains-mobile`. Status semantics:
- Done = success green
- In progress = info blue
- Not started = neutral gray
- Flagged / warning = amber
- Skipped = muted gray + strikethrough on item label

**Contrast** — Designed for outdoor / sunlight readability. Aim for WCAG AA 4.5:1 on body text against light surfaces; AAA where feasible. Avoid pure-gray on white; use slightly darker text colors than typical web designs.

**One-handed thumb reach** — Primary actions in the lower half of the screen. Pinned bottom action bar on ticket detail puts "Mark complete" in the bottom-right thumb zone. Respect `useSafeAreaInsets` everywhere.

**Network state** — Persistent thin status indicator (in the header or as a small floating chip) shows offline/sync state when not online. Tap → upload queue sheet.

**i18n** — Reuse the existing i18n approach if `highplains-mobile` has one; otherwise add `i18n-js` + `expo-localization` and parity the keys with the web app's `en` / `es` translations. All user-facing strings go through i18n. Mark new `es` keys with `// TODO: human-review translation`.

**Multi-tenancy** — Every API call still filters by `companyId` from the authenticated user context. The mobile client does not select or pass `companyId` explicitly — it is derived server-side from the auth token.

**Native APIs (Expo)** — Reuse what's already installed in `highplains-mobile`. Likely candidates: `expo-camera`, `expo-image-picker`, `expo-file-system`, `expo-notifications`, `expo-secure-store`, `expo-constants`, `expo-linking`, `expo-localization`, `@react-native-async-storage/async-storage`, `@tanstack/react-query`. Inspect the `package.json` before adding any of these — do not duplicate.

**Routing** — Use the existing routing approach in `highplains-mobile` (Expo Router file-based vs React Navigation stack/tab). Match whatever convention is there.

**Styling** — Use whatever styling approach is already in `highplains-mobile` (NativeWind, StyleSheet, restyle, etc.). Do not introduce a new one.

**Image handling** — Compress captured images client-side to max 2048px long edge using `expo-image-manipulator` before upload. Strip EXIF location data; preserve orientation only.

## 7. Open questions to revisit (not blocking v1)

- Per-item photos vs ticket-level only — currently ticket-level. Revisit if "photo required" items are common enough to warrant per-item attachment.
- Voice-to-text notes — likely valuable for gloved supervisors but not v1.
- Crew chat / direct message to admin — possibly a v1.5 layer over flagging.
- Materials usage logging — irrigation/landscape needs this; maintenance generally doesn't.
- Time tracking depth — if accountability needs grow, layer per-item or per-employee time later.
- Customer signature on completion — for ad-hoc / extra work tickets, may be needed eventually.
- Native map view on the property Map tab (using `react-native-maps`) vs the simpler static-image-from-web-export approach used in v1.
- Background location for auto-arrival detection — interesting but adds permission friction.

## 8. Implementation slices

> **Slice conventions** (read before any slice):
>
> - Each slice lands in a deployable state across **both** the web app (backend extensions) and the Expo app (mobile UI).
> - **Critical: do NOT replace existing systems.** The web app's ticket, property, customer, campaign, and auth systems already work. The Expo app already exists with its own conventions. **Inspect both before writing code.**
> - **Web stack:** React 18 + TypeScript + Vite + Tailwind + shadcn/ui (Radix) + Wouter + TanStack Query v5 + React Hook Form + Zod + Drizzle ORM + Postgres + i18next.
> - **Mobile stack:** Expo + React Native + TypeScript. Routing, styling, state management, and auth conventions are whatever `highplains-mobile` already uses — inspect and match.
> - Multi-tenancy: every table has `companyId`, every query filters by it. No exceptions.
> - Mobile API endpoints mount under `/api/m/*` in the web app's Express routes.
> - All user-facing strings go through i18n on both sides; new keys land in `en` and `es` with `// TODO: human-review translation` markers on `es`.
> - File uploads reuse the existing storage layer (the same one used for chemical-label PDFs and customer attachments). Do not introduce a new file backend.
> - Web loading state = shadcn Skeleton. Web error state = shadcn Alert. Web icons = `lucide-react`. Mobile loading/error/icon conventions: match what's in `highplains-mobile`.
> - At the end of each slice, report back with: files created (both projects), files modified, schema/columns added, API endpoints added, mobile screens/components added, manual test plan, decisions made where prompt was ambiguous, anything skipped with reasons.

### Slice 0 — Mobile foundation: auth flow, navigation scaffold, role gate

#### Context

Establish the foundation in the existing Expo `highplains-mobile` project: a working token-based authentication flow against the web API, a bottom-tab navigation with three screens (Today / Properties / Me), a header with the "+ Flag" entry point (still placeholder), and a role gate that ensures only crew supervisors can use the app. Real data and features come in later slices.

This slice also adds (on the web side) the `crews` concept needed for everything downstream.

#### Existing context to inspect (both projects)

**Web app:**
- `users` table in `shared/schema.ts` — check what role field/values already exist. Roles may be free-text, an enum, or a separate `userRoles` table. Add `crew_supervisor` to the existing set; do NOT introduce a parallel role system.
- Existing auth — find how the web app issues sessions. The mobile app needs a **token-based** flow (likely JWT or opaque bearer tokens). If a mobile token flow already exists in the codebase, reuse it. If not, add one in this slice (a new login endpoint that returns a token + a middleware that validates tokens alongside the existing session middleware).

**Mobile app (`highplains-mobile`):**
- Inspect `package.json` for Expo SDK version, navigation library, styling library, state management.
- Inspect the existing route/screen tree if any.
- Inspect any existing auth flow (login screen, token storage). If one exists, extend it rather than replacing.
- Confirm `expo-secure-store` is available for token storage (preferred over AsyncStorage for secrets).

#### Schema changes (web app)

**1. `users` role addition**

Verify whether `crew_supervisor` exists as a valid role. If roles are free-text with a Zod-validated set, add `crew_supervisor` to that set. If a normalized table, add the row. If `foreman` or similar already exists and admin confirms it's the right concept, use it instead — document the decision.

**2. New table: `crews`**

A crew is a named group led by one supervisor. v1 has one supervisor per crew.

Fields:
- `id` — varchar, PK, UUID
- `companyId` — varchar, FK → `companies.id`, not null
- `name` — text, not null
- `supervisorUserId` — varchar, FK → `users.id`, not null
- `isActive` — boolean, not null, default true
- `createdAt`, `updatedAt`

Unique on `(companyId, name)`. Index on `(companyId, supervisorUserId)`.

**3. New table: `mobile_auth_tokens` (only if a token system doesn't already exist)**

- `id` — varchar, PK, UUID
- `companyId` — varchar, FK, not null
- `userId` — varchar, FK → users, not null
- `tokenHash` — text, not null (store hash, never raw token)
- `deviceLabel` — text, nullable (e.g., "Jose's iPhone 13")
- `lastUsedAt` — timestamptz
- `expiresAt` — timestamptz, nullable
- `revokedAt` — timestamptz, nullable
- `createdAt`

Index on `tokenHash`. Tokens expire after 90 days of inactivity; refreshed on every use.

**4. Migrations** — Idempotent `IF NOT EXISTS` startup pattern matching existing migrations in `server/index.ts`.

#### API endpoints (web app)

- `POST /api/m/auth/login` — body: `{ email, password, deviceLabel? }`. Returns `{ token, user: { id, name, email, role }, crew: { id, name } | null }`. Validates credentials reusing the existing password verification logic. Creates a `mobile_auth_tokens` row. If the user is not a crew supervisor, return 403 with a clear message.
- `POST /api/m/auth/logout` — revokes the current token. Requires bearer auth.
- `GET /api/m/me` — returns the current user, their role, and their crew. Used by the mobile shell to verify the token and load crew context.
- `GET /api/crews` (admin/office only) — list crews for the company.
- `POST /api/crews` (admin/office only) — create crew.
- `PATCH /api/crews/:id` (admin/office only) — update crew.

**Token middleware** — Add an Express middleware that accepts `Authorization: Bearer {token}`, hashes it, looks up the row, populates `req.user` (and `companyId` via the user), and rejects revoked/expired tokens. The middleware coexists with the existing session middleware so the same routes can serve both web sessions and mobile tokens. Mount this middleware on all `/api/m/*` routes.

#### UI changes — Web app

**Admin: Crews settings page**

New route `/dashboard/settings/crews`. Standard CRUD table matching the chemical-products page pattern (`/dashboard/settings/chemical-products`):
- Columns: Name, Supervisor (user), Active toggle, Edit/Delete
- Add/edit modal: name field + searchable supervisor select (users with `crew_supervisor` role)
- Add to the existing settings nav

#### UI changes — Mobile app

**1. Auth flow**

- Login screen: email + password fields, "Sign in" button, app logo. Submit calls `POST /api/m/auth/login`. On success, store the token in `expo-secure-store` and navigate to the main app. On 403 (not a supervisor), show a friendly "Mobile access is for crew supervisors. Contact the office." message.
- A `useAuth()` hook (or extend an existing one) that exposes `user`, `crew`, `signIn`, `signOut`, `isLoading`. On app boot, the hook reads the token from secure storage, calls `GET /api/m/me`, and routes to the main app or the login screen accordingly.
- A logged-out state should show the login screen as the root; logged-in state shows the bottom tab nav.

**2. Navigation scaffold**

Match the project's existing convention (Expo Router or React Navigation). Implement:
- Bottom tab navigator with three tabs: **Today** (default), **Properties**, **Me**
- Each tab is a stack so deep navigation (e.g., Today → Ticket Detail) stays inside the tab
- Header in each tab: left title slot, right "+ Flag" button (opens a placeholder alert for now — real flow in Slice 4)

Tab icons: choose from `@expo/vector-icons` (likely already installed) — e.g., `Ionicons` `calendar-outline`, `map-outline`, `person-outline`.

**3. Placeholder screens**

`Today`, `Properties`, `Me`, `TicketDetail`, `PropertyDetail` screens — each renders "{Screen} — coming in Slice {N}" centered in safe area.

**4. App configuration**

- Update `app.json` / `app.config.ts` with the correct name ("High Plains CRM"), short name, splash screen background matching brand, app icon. Reuse `attached_assets/NEW - LOGO-03_1763582979034.png` or similar — generate properly sized icons for iOS and Android if not already present.
- Confirm bundle identifiers (`ios.bundleIdentifier`, `android.package`) — these are set once and should not change after first submission to App Store / Play Store. If unset, propose `com.highplains.crm` and confirm with admin before publishing.
- Configure deep linking scheme (`scheme: "highplainscrm"`) for future use (e.g., admin web app linking back to mobile).

**5. API client**

A small wrapper around `fetch` (or whatever the project uses) that:
- Reads the token from secure storage
- Attaches `Authorization: Bearer {token}` to every request
- Points to the correct base URL (configurable via `expo-constants` `extra` field for dev vs prod)
- Handles 401 by clearing the token and redirecting to login
- Returns parsed JSON

If the project already has an API client, extend it.

#### Patterns and conventions

- Mobile React Query keys prefixed with `m-` to keep namespacing clear.
- Token never logged or stored unencrypted; always via `expo-secure-store`.
- Login screen and main app are different navigators (a `RootNavigator` that switches based on auth state).

#### Out of scope for this slice

- Real ticket/property/flag data — placeholders only
- Camera, photo capture
- Push notifications (setup comes in Slice 6)
- Offline cache beyond what React Query gives us by default
- Biometric unlock (Face ID / fingerprint) — v1.1
- Password reset from mobile — direct users to web

### Slice 7 — Offline cache + sync queue + polish

#### Context

Harden the field experience: today's tickets and site notes are cached on launch so they read in dead zones, mutating endpoints (work item state changes, notes, completion) queue and retry offline, sync indicator shows pending/failed state, polish gaps left in earlier slices.

#### Existing context to inspect

**Mobile:** The Slice 3 upload queue handles multipart photo uploads. Extend it to handle JSON mutations too, or keep them separate — designer's choice; whichever matches `highplains-mobile` patterns better.

#### Schema changes

None.

#### API endpoints (web)

- `GET /api/m/sync` — single endpoint that returns the bundle to operate offline for today:
  ```ts
  {
    today: { /* same as /api/m/today */ },
    tickets: [ /* full /api/m/tickets/:id payload for each today's ticket */ ],
    properties: [ /* curated subset for each of today's properties */ ]
  }
  ```
  Called on app foreground and on pull-to-refresh from Today.

#### UI changes — Mobile

**React Query persistence** — Use `@tanstack/react-query-persist-client` with AsyncStorage. Persist all `m-*` query keys. Cache TTL 24h. On app launch, restore from persistence immediately, then revalidate in background.

**Mutation queue** — Extend Slice 3's upload queue to handle:
- Check/uncheck/skip work item (`PATCH /api/m/work-items/:id`)
- Complete ticket (`POST /api/m/tickets/:id/complete`)
- Add note (`POST /api/m/tickets/:id/notes`)
- Submit flag (`POST /api/m/flags`)

Mutations apply optimistic UI updates immediately via React Query's `onMutate`. On offline detection, queue and retry on reconnection. On server rejection (e.g., 409 on completion with missing items), surface the error to the user and revert optimistic UI.

**Sync indicator** — Small chip or icon in header:
- Green dot → online, nothing pending
- Cloud arrow + count → uploads pending
- Amber warning → failures (tap → sheet with retry/dismiss list)
- Gray cloud → offline (cached data in use)

**Offline detection** — Use `@react-native-community/netinfo` if not already installed.

**Polish pass** — Walk every screen:
- Skeleton loading states (no full-page spinners)
- Error states with retry
- Empty states with helpful copy
- Confirm safe-area insets honored on iPhone 14+ Dynamic Island devices
- Confirm tap targets ≥ 44pt everywhere

#### Out of scope

- Full offline-first creation of new tickets (admin web-only in v1)
- Two-device edit conflict resolution beyond last-write-wins (foreman-only assumption makes conflicts unlikely)

#### Deliverables

Standard. Manual test: enable airplane mode, foreground the app, today loads from cache. Open a ticket, check items, observe UI updates immediately. Capture a photo. Exit airplane mode; observe everything syncs in order. Force a server failure mid-sync; observe the failed-uploads sheet with retry.

## 9. Glossary

- **Ticket** — A single visit by a crew to a property to perform one or more services. Atomic unit of field work.
- **Work item** — A checkable line inside a ticket. Has status, optional instruction, optional photo requirement.
- **Stop** — User-facing word for a ticket on the Today screen. Internally still a ticket.
- **Crew** — A team led by one supervisor. v1: one supervisor per crew.
- **Crew supervisor (foreman)** — The authenticated mobile user. The only role with mobile access in v1.
- **Site notes** — Curated property information shown at the top of a ticket. Filtered for relevance to the ticket's service type.
- **Flag** — A field-discovered issue captured as photo + tag + optional note, sent to the admin inbox.
- **Service type** — A category of work used to drive work-item templates and site-note filtering.
