# F2: Scheduling dates use the Colorado calendar day, not the server's

> Standalone slice; run it after F1. Read `.agents/memory/colorado-calendar-days.md` first. Line numbers are from GitHub `b2dd122`; find code by its content. **No schema change, no migration.** Tests use vitest and run under `TZ=UTC` **and** `TZ=America/Denver`. Report changed files, call sites, test results and baseline failures separately.

## Why

Phase 2 assumed the server's local time is Colorado time. C2 found the development host runs **UTC**, and production almost certainly does too. Today's code works out "today" from the server's clock (`localDateString`, `setHours(0, 0, 0, 0)`). On a UTC server, the date rolls over at **6 pm Colorado time (5 pm in winter)**. That causes three problems:

- **Schedule-by dates** for jobs created in the evening come out one day late.
- **"Past schedule-by", "Follow-ups due" and "today" on the Dashboard** switch to tomorrow's date every evening, and the server and the web app (which already uses America/Denver) disagree for those hours.
- **The crew app's Today and week views** show tomorrow's stops after about 6 pm.

Phase 3 puts dates on every visit, so this has to be correct first.

**Don't fix this by changing the server's timezone.** The `pg` driver reads `timestamp` columns from raw SQL as local time, so changing the server's `TZ` would shift every stored timestamp. Make the Colorado day explicit instead.

## 1. One set of helpers: `artifacts/api-server/src/lib/companyDay.ts`

```ts
export const COMPANY_TIME_ZONE = "America/Denver";
/** The Colorado calendar date (YYYY-MM-DD) that an instant falls on. */
export function companyDateString(instant: Date): string
/** Colorado "today". */
export function companyToday(now?: Date): string
/** Start (inclusive) and end (exclusive) instants of a Colorado calendar day, DST-correct. */
export function companyDayBounds(date: string): { start: Date; end: Date }
/** Pure calendar arithmetic on YYYY-MM-DD strings (no host timezone involved). */
export function addCalendarDays(date: string, days: number): string
export function isWeekend(date: string): boolean
```

Use `Intl.DateTimeFormat(…, { timeZone: COMPANY_TIME_ZONE })` to read an instant's Colorado date. Use `Date.UTC` arithmetic for day math on date strings. `companyDayBounds` must give 23-hour and 25-hour days on the two daylight-saving changeover dates.

## Tests (run under TZ=UTC and TZ=America/Denver)

- **`companyDateString` at boundaries:** `2026-10-09T23:30:00-06:00` is `2026-10-09`, not the 10th. Midnight in Colorado is the new day. DST start (Mar 8, 2026) and end (Nov 1, 2026) are both correct.
- **`computeScheduleBy`:** a job created at 7 pm on Friday Oct 9 with urgent priority is due Monday Oct 12 under both TZ values. Every other priority case still passes.
- **Dashboard queue:** a schedule-by of yesterday shows as Past schedule-by at 8 pm Colorado time under `TZ=UTC`.
- **Crew app `GET /api/m/today`:** at 8 pm Colorado time under `TZ=UTC` it returns today's Colorado date and today's stops, not tomorrow's.
- All existing scheduleBy, queue, backfill and owner-response tests still pass.
