Visual Scope Sheet — Slice VS5 (Finalize-Grade Freezing of Visual Scope Snapshots) — Submit This Whole Block
Goal

Complete the Visual Scope Sheet tool by ensuring finalized proposal versions are fully immutable, including any attached Visual Scope visuals. When a proposal is finalized (P5), any attached Visual Scope exports must be rendered once, stored permanently, and tied to that specific proposal version so that future edits to the Visual Scope Sheet never change past finalized proposals.

Guardrails (What NOT to build)

Do not add multi-scope per proposal (still one Visual Scope per proposal)

Do not add new editor tools, measurement, or GIS features

Do not add templates, email delivery, approvals, or automation

Do not change Visual Scope rendering logic (reuse VS3 renderer)

Keep changes focused on finalization integrity and auditability

Core Principle (Immutable Snapshot Integrity)

A finalized proposal version must be self-contained:

The frozen PDF is stored (already in P5)

Any Visual Scope images included in that version are also frozen and stored

Finalized version downloads and views must rely only on frozen artifacts, not live rendering

Requirements
1) Freeze Visual Scope Images During Proposal Finalization

Enhance the proposal finalization flow (POST /api/proposals/:id/finalize) so that:

If the proposal has an attached Visual Scope Sheet (visualScopeSheetId set):

Render the required Visual Scope PNGs server-side using the existing VS3 renderer:

Always generate combined PNG

Generate base-only PNG only if the proposal’s “Base-only page” flag is enabled

Generate overlay-only PNG only if the proposal’s “Overlay-only page” flag is enabled

Store the generated PNGs permanently in GCS under the proposal version folder:

{privateObjectDir}/proposal-versions/{proposalId}/v{versionNumber}/
  visual-scope-combined.png
  visual-scope-base.png        (only if enabled)
  visual-scope-overlay.png     (only if enabled)

The finalization must be fail-safe:

If any required Visual Scope render or upload fails, the entire finalization fails

No proposal_versions row is inserted

No “partial” frozen assets are left without a corresponding version record

If a failure occurs after some uploads, log a cleanup warning (or delete partial files if simple)

2) Store Visual Scope Snapshot Metadata on the Proposal Version

Extend the proposal version record to store a snapshot reference to frozen Visual Scope assets.

Add fields to proposal_versions (or a JSONB meta field) to store:

visualScopeSheetId (nullable)

visualScopeTitle (snapshot)

visualScopeDate (snapshot)

visualScopeExportWidth (e.g., 2000/3000)

visualScopeIncludedBase (boolean)

visualScopeIncludedOverlay (boolean)

visualScopeFrozenAt timestamp

visualScopeCombinedPath (GCS path)

visualScopeBasePath (nullable GCS path)

visualScopeOverlayPath (nullable GCS path)

Important: These fields must represent the state at the time of finalization and must not change.

3) Ensure Finalized Proposal Versions Never Use Live Visual Scope Rendering

For finalized versions:

Any display of Visual Scope imagery for a version must use the frozen PNG paths stored on the version record.

Finalized versions must never call live VS export endpoints (/export/*) to reconstruct history.

4) Version Page UI: Visual Scope Snapshot Visibility (Admin/Office)

On the finalized proposal version page (ProposalVersion view):

If that version includes a frozen visual scope snapshot, show a small section:

“Visual Scope Snapshot (Frozen)”

Title + date

Frozen timestamp

Links/buttons (optional but preferred):

Preview/Download Combined PNG

Preview/Download Base PNG (if included)

Preview/Download Overlay PNG (if included)

These should stream directly from the frozen GCS objects.

5) Permissions

Admin + Office: can finalize and view/download frozen Visual Scope assets for versions

Other roles: no access (unless specified later)

Acceptance Tests
Test A — Finalize With Visual Scope Attached

Create a proposal draft with:

attached Visual Scope Sheet with base image and markup

Base-only flag ON, Overlay-only flag ON

Finalize proposal → creates v1

Confirm in GCS:

visual-scope-combined.png exists

visual-scope-base.png exists

visual-scope-overlay.png exists

Version page shows “Visual Scope Snapshot (Frozen)” with correct title/date and working preview/download links

Test B — Immutability

After v1 finalized, edit the Visual Scope Sheet markup (move symbols, add polygon)

Re-download v1 and/or view v1 frozen PNGs

Confirm visuals are unchanged (still match the original frozen snapshot)

Test C — Flags Behavior

Finalize a proposal with only Base-only enabled

Confirm only combined + base are frozen (no overlay)

Finalize a proposal with neither flag enabled

Confirm only combined is frozen

Test D — Fail-Safety

Force a failure during Visual Scope rendering or GCS write (simulate missing base image or throw in renderer)

Confirm:

finalize returns a clear error

no proposal_versions row is created

no partial version is visible in UI

Done Definition

Finalized proposal versions become fully immutable and self-contained: when a Visual Scope is attached, the exact combined/base/overlay visuals used in that version are rendered once, stored permanently, referenced by the version record, and remain downloadable forever regardless of future edits to the draft or Visual Scope Sheet.
